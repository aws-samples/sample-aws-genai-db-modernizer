# Answer-key review sheet: wordpress

Blind review sheet for the `final_assignment` benchmark key of the `wordpress` sample (`docs/examples/wordpress/wordpress.zip`, #1074). It lists 163 queries in 26 sections, 118 distinct shapes. It shows the facts routing reads and never the engine the pipeline picked or any score, so the key is not anchored on today's output. Generated by `uv run python -m benchmarks.runner.review_sheet --sample wordpress`; do not edit the facts columns by hand.

## How to fill it in

- `acceptable`: every engine that would be a defensible home for the query, comma separated, using these ids: `dynamodb`, `documentdb`, `opensearch`, `elasticache`, `aurora_postgresql`, `aurora_mysql`.
- `ideal`: the one best engine, only where one is clearly best (optional). It must be in `acceptable`.
- `rationale`: a few words a later reviewer can check against the facts.
- `=N`: same answer as row N (acceptable, ideal and rationale). The `shape` column suggests N where an earlier row has the same access path, tables and operation.
- A section's **Default** line: fill it in and leave a row empty to inherit it; a filled row overrides it.
- `?`: unsure, discuss before the key is written. `-`: leave out of the key.
- A co-dependency group's members always land on one engine, and a table's writes (its write group, the `W:` marks) share one engine: answer them consistently. Reads may sit elsewhere as replicas.
- When the sheet is done, the key (`expected.json`) is written from it with the maintainer and set `reviewed: true`, with the case's floor added to `gate.json`.

Column meanings:

- `id`: the query id (a unique prefix when the id is long). `op`: the statement type. `calls/s` and `share`: its call rate and share of all the sample's calls.
- `tier`: **A** = the busiest queries that together make 90% of calls, **B** = the next ones up to 99%, **C** = the rest (and every query with no recorded calls). Shares for tiers leave out utility statements (`-`): `BEGIN`, `SET`, `SHOW` and the like read no table data, so they sit in one section at the end, where one Default line can answer them all.
- `groups`: `CDn` = member of co-dependency group n; `W:table` = writes that table (member of its write group).
- `class` and `access path`: the query's access-pattern class and the reason it was classed so (ADR-031 Decision 14). `facts`: pattern facts (write, upsert, partition_range, ...) and collector flags (joins, aggregation, subquery, text search, average rows returned, median latency).

## Proposed review order

1. Tier A rows (26 queries, 90% of calls): read each one.
2. Tier B rows (58 queries): answer with `=N` where the `shape` column offers one, otherwise read the row.
3. Tier C rows (60 queries, under 1% of calls): set each section's Default, then only override the rows that differ; `=N` covers most of the rest.
4. Sections run busiest first, so stopping early still covers the traffic that matters most; an unanswered row stays out of the key.
5. The utility section (19 statements) last; a section Default line answers them all at once.
