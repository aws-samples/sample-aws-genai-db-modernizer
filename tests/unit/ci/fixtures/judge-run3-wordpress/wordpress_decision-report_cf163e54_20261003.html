Executive summary

The WordPress and WooCommerce workload moves to a hybrid target built on DynamoDB, ElastiCache, and Aurora MySQL. DynamoDB serves the largest share of the workload, 63 of 107 queries, covering key-based reads and writes such as option lookups, post reads, and metadata access. ElastiCache takes 34 queries that benefit from in-memory latency, and Aurora MySQL keeps the 10 queries that need relational joins and text search, so no query is forced onto an engine that fits it poorly. The migration removes the single relational bottleneck, lets each access pattern scale on the service built for it, and leaves the relational core only where joins are required.

Risk posture

Overall risk MEDIUM. 11 migration risks identified (2 high, 9 medium) across migration complexity, operational risk, performance degradation. The full risk register, with per-engine detail and mitigations, and the migration trade-offs are in the Engineering Report.

Mitigation strategies

  • Run load tests with production-scale data before migration to validate performance targets
  • Implement unsupported patterns (text search, aggregations) via Aurora MySQL (full-text indexes, SQL aggregation), application-layer computation
  • Refactor stored procedures, triggers, and views into application logic before migration
  • Use blue-green deployment with rollback capability for high-risk table migrations
  • Monitor target database metrics closely during the first 2 weeks post-migration
