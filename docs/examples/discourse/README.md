# Discourse on PostgreSQL 16: the PostgreSQL sample

`discourse.zip` holds `discourse-collection.json`, a PostgreSQL 16 collection of a Discourse forum: 311 tables and 1,654 queries in the `discourse` database. The load and the data are synthetic; there is no customer data.

## The routine set

The collection was taken before routine code was collected: it lists 266 functions and aggregates by name only, most of them owned by the `hstore`, `citext`, `pg_trgm`, `unaccent` and `vector` extensions. The routine phase reads none of those rows, so they are neither carried nor a routine to migrate yourself; the run log counts them (#2124). Its 3 triggers keep their action statement but no `CREATE`, so each is a routine to migrate yourself. `discourse-routines.json` adds a small synthetic set with bodies (#1954), in the sections `scripts/collect-postgresql.sql` writes (`procedures`, `triggers` and `metadata.routine_capture`). Each is written for this schema, not copied from Discourse:

| Routine | Kind | Outcome |
|---|---|---|
| `topic_visible_post_count(integer)` | SQL function | carried as it is |
| `prune_read_notifications(integer)` | PL/pgSQL procedure | carried as it is |
| `posts_bump_topic` | trigger on `posts` | carried as it is |
| `posts_bump_topic()` | PL/pgSQL trigger function | rewritten: its owner becomes the target user |
| `begin_upload_snapshot(text)` | PL/pgSQL procedure | can't be carried: it starts a base backup, which Aurora PostgreSQL does not let a session do, so it is the HIGH "migrate it yourself before wave 1" to-do |

The deterministic end-to-end run (`tests/e2e/pipeline.py`, and `scripts/build_docs_sample.py --deterministic --sample discourse`) adds the set to the collection before it collects, so the run goes through the routine phase like any collection with routines; `tests/e2e/test_sample_routines.py` checks each outcome in `report.json`, the engineering report and the results page, and the routine headline and to-do in the executive report and the final summary. <!-- claim: tests/e2e/test_sample_routines.py::test_each_synthetic_routine_gets_its_outcome, tests/e2e/test_sample_routines.py::test_the_routine_that_cannot_be_carried_is_a_high_to_do_that_holds_no_wave, tests/e2e/test_sample_routines.py::test_the_engineering_report_states_each_outcome, tests/e2e/test_ui.py::test_results_page_states_the_routine_outcomes, tests/e2e/test_sample_routines.py::test_the_executive_report_and_the_final_summary_print_the_routine_facts --> `tests/e2e/test_sample_routine_scripts.py` takes the same run on to step 1: the 4 carried routines are in `routines-deploy.sql`, in one transaction with the trigger created disabled, and `triggers-enable.sql` enables it; on a local PostgreSQL standing in for Aurora, both scripts and their read-only checks run and every carried routine is confirmed, while the gate's routines check still fails on `begin_upload_snapshot`, not carried, and the triggers-enable check on the 3 old triggers. <!-- claim: tests/e2e/test_sample_routine_scripts.py::test_the_deploy_script_creates_the_carried_routines_in_order, tests/e2e/test_sample_routine_scripts.py::test_the_triggers_enable_script_turns_on_what_step_1_left_off, tests/e2e/test_sample_routine_scripts.py::test_the_postgresql_scripts_deploy_and_check_on_a_stand_in_target --> A run of the zip alone has those 3 triggers as its only routines.

### The set on a source database

For the step 1 rehearsal the set has to be on the forum's own PostgreSQL source, so that a collection taken there holds it and step 1 carries it to the rehearsal Aurora. `discourse-routines-install.sql` creates it there, in one transaction, and `discourse-routines-remove.sql` drops it again. Both are rendered from `discourse-routines.json` by `uv run python scripts/render_sample_routines.py` (`--check` names a stale file). Run the install with psql in the `discourse` database, after the schema is loaded, as a user that may give routines to the `postgres` and `discourse` roles. Once installed, the trigger sets a topic's `bumped_at` on each new post, so remove the set when the rehearsal is done. Installed on a local PostgreSQL and collected, the set comes back as the same routine sources, owners included, that the JSON set gives the end-to-end run. <!-- claim: tests/unit/scripts/test_render_sample_routines.py::test_the_committed_scripts_are_the_rendered_ones, tests/unit/scripts/test_render_sample_routines.py::test_the_discourse_install_collects_back_to_the_bundled_set -->
