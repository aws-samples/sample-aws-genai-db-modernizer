# Understand the results

This describes the deliverables the pipeline produces today.

## The pipeline, in plain terms

1. **Collect** parses the source database's schema and query patterns.
2. **Triage** looks at workload signals (key-value lookups, text search, time-series, etc.). Every engine that can own a query is analyzed and scored; the signals are evidence for an engine, not a filter. The ElastiCache cache layer, which owns no query, is analyzed only when one of its signals fires.
3. **Analyze** scores every query against each engine triage selected, deterministically.
4. **Assign** routes each query to its best-scoring engine. Co-dependent queries (joins across the same tables) move together, and all of a table's writes land on one engine, the table's source of truth; another engine can still serve the table's reads from a copy kept in sync.
5. **Reality Check** removes an engine once the engines that remain can serve its queries just as well, and moves each of its queries onto its own best-fit remaining engine. A model's flag on a moved query re-routes it only among the engines that remain; it never brings a removed engine back. <!-- claim: tests/unit/agents/referee/test_reality_check_request.py::TestAFlagOnWordpressNeverBringsBackDocumentDB::test_one_flag_goes_to_the_best_kept_engine, tests/unit/agents/referee/test_reality_check_llm_seam.py::TestApplyLlmOutputHandlesCorrectionsAndSummary::test_a_flag_never_brings_back_the_removed_engine --> The source-compatible Aurora engine survives this consolidation unless another engine scores better, or is at least 40% and $100/month cheaper. <!-- claim: tests/unit/agents/referee/test_source_compatible_tie_survival.py::TestTheIssueRepro, tests/unit/agents/referee/test_source_compatible_tie_survival.py::TestANonTieIsUnaffected, tests/unit/agents/referee/test_source_compatible_tie_survival.py::TestTheCostException --> A model can check that each move still works; the consolidation itself is deterministic and does not need it.
6. **Schema Design** produces concrete schemas per engine: DynamoDB table definitions, DocumentDB collections, OpenSearch mappings, the relational DDL that stays.
7. **Synthesis** produces the final report: ranking, TCO, the migration roadmap, risks, and an executive summary.

Collect through Reality Check never needs a model. Schema Design and the Synthesis executive summary do.

## The results page

`/modernize` links each job's results page at the end of the run (`http://localhost:3000/analysis/results/<job_id>`). It leads with the headline and keeps the detail one click away. From the top:

1. **Three download buttons** for the files above: Executive Summary (`executive-report.pdf`), Engineering Report (`engineering-report.md`) and Assessment Detail (`assessment-data.json`).
2. **Executive summary**: three short paragraphs, the same text the engineering report opens with. **Recommendation** names the target services, the share of queries each takes, the wave order and the projected monthly cost with its price basis (with no current cost collected for the source, it says so and claims no saving); **Risk** gives the overall risk level and the one or two risks driving it, with the wave to act before; **Decision** says what to approve next (normally wave 1) and why it is safe. Below it: the number of queries, the current and projected cost and the saving.
3. **Query flow**: a Sankey diagram of the queries from the source to their engines.
4. **Cost breakdown**: the projected monthly cost per engine.
5. **Migration roadmap**: the waves, each with its gate; a table list in a gate opens in place.
6. **Banners**, when they apply: queries on a fallback engine, the access patterns an unresolved DynamoDB merge leaves unserved, the DynamoDB merge-review decisions, and close calls (queries whose engine scored less than 5 points above another engine the plan keeps).
7. **Query routing**, collapsed: every query and its engine, with search and filters; open a query to see its history and why it ended on its engine.
8. **Access pattern explorer**: the target data model, by access pattern or by source table, filtered by engine, operation or table (on a run with access patterns).
9. **Table owners**, collapsed: each mapped table's owner, the engines that also read it and the cache in front of it, as in the engineering report's Migration map.
10. **Sources of truth and replicas**, collapsed: each written table's source of truth, its replicas, the CDC direction and the reads a replica serves.
11. **Risk assessment** (the open risks by severity, and the risks the assignment already resolved in a collapsed list), **Trade-offs and design decisions**, and **Table design**: the Aurora design (its tables, DDL, optimizations and the queries routed to it), each part in a collapsed section; each tab names the tables in that engine's design, which is not the roadmap's count of source tables and views (wave 1 counts every source table, including those no query reads); it appears once schema design has run. The other engines' designs are in the access pattern explorer.

When the local API runs with the experimental graph explorer on, the page also has an **Explore (experimental)** button that opens the job's graph; see [Explore the graph](explore-the-graph.md). Without it the page is as above.

## How to read an assignment

Assignments map **queries** to engines, not tables. Several engines can serve the same table. The deliverables state one line per source table, computed from the final assignment:

- **Owner**: the same owner the migration waves name. It is the engine that takes the table's writes (a table has one writer). A table no query writes is owned by the engine that serves most of its queries; a tie goes to the source-compatible Aurora engine the plan keeps. When a table's writes still sit on more than one engine, the map says "no single writer" next to the owner the waves name, and Sources of truth lists the table with no source of truth. A cache or search engine never owns a table, so a table the cache design keys still has its system-of-record owner and counts where that owner's tables count.
- **Also read by**: every other engine whose queries read the table. It reads a copy kept in sync from the owner via CDC.
- **Cached by**: the cache in front of the table's reads (ElastiCache), when one is.

The "recommended engine" in a `table_mappings` entry is the schema design that maps the table with the highest fit; it does not make that engine the owner. Each entry also carries `owner`, `owner_basis`, `also_read_by` and `cached_by`, and `facts.table_owner_lines` has the same lines and their counts. Each engine's confidence score is the mean fit of the queries actually routed to it, not every table it was evaluated against; a score with no table-level evidence behind it is labelled "signal only."

## The cache layer

ElastiCache is recommended only for hot reads, as a cache-aside layer in front of each cached read's owner engine. This is the tool's recommendation, not a limit of the service: the cached reads are hot, small and can be rebuilt from their owner, so the owner (Aurora, DynamoDB or DocumentDB) stays the system of record and the cache is sized for the hot reads, not the whole dataset. In the plan the cache never owns a query, and if it is lost the owner still has every row. [ElastiCache for Valkey 9.0 and later offers durability](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/durability.html) on Multi-AZ clusters, with synchronous or asynchronous writes; the tool does not use it as a system of record today. ## OpenSearch as a read model

OpenSearch serves search and analytics queries, but every table it serves keeps a durable owner elsewhere. OpenSearch is kept in sync with that owner and never holds the only copy. If the index is lost, you re-index; no data is lost.

## Migration waves

The deliverables lay out a suggested step-by-step path that starts with the relational move. For example: Wave 1 moves the source database to Aurora with no data model changes yet; Wave 2 adds a cache layer in front of the hot reads; Wave 3 moves key-value queries to DynamoDB; Wave 4 adds OpenSearch as a read model for search and analytics queries. The fully decomposed target architecture appears next to it as the direct, single-step option. The wave order is a suggestion; other orders work too, and the end-state schema is the same either way.

Each wave lists every table its queries use, not only the tables its engine owns, and the engineering report shows both numbers as "N source tables (M to move)". The tables that move go to the wave's engine. The rest stay owned by their current engine (usually Aurora) and are kept in sync from that owner via CDC. Each wave ends with a gate: what to validate before the next wave starts. For a SQL Server or Oracle source, wave 1 converts the whole schema to the chosen Aurora engine, and the plan says that this wave is not yet optimized for heterogeneous migrations.

## Sources of truth and replicas

All of a table's writes land on one engine, its source of truth. When another engine serves some of the table's reads, it reads a copy kept in sync from the source of truth via CDC, so those reads are eventually consistent. The engineering report and the results page list each written table's source of truth, its replicas, the CDC direction and how many reads run on a replica, and the risk register carries the consistency risk.

## Close calls

A close call is a query whose engine scored less than 5 points above another engine the plan keeps, which could serve it too. The assessment still decides, deterministically; the engineering report and the results page list them so you can move any of them yourself in the assignment review. Exact ties a routing rule settled are counted apart from them.

## Unresolved DynamoDB merge conflicts

DynamoDB is designed in parallel query groups, and their designs are merged into one. When two groups design the same table differently and the merge cannot reconcile them, it keeps one design and fails validation. `/modernize` sends the conflict back to the designers, but a run with no fix round (`--llm-mode bedrock`) keeps it. The engineering report and the results page then list each conflict under "Access patterns the merged DynamoDB design does not serve": the failure, and the access patterns and queries it concerns. Patterns are **not served** when the merged design runs them on a table or index that was not designed for them (the dropped design's patterns, or a pattern on a table or index the design does not define). They are **at risk until the conflict is resolved** when they run on a table the failure concerns: one that cannot be created as designed (more global secondary indexes than the default limit, a name over 255 characters), the tables holding rows with contradictory keys, or rows the merge could keep no safe key for. A failure that names no access pattern says so. A design merged before the assessment recorded these lists says its unserved patterns were not recorded; merge it again to list them. The executive report states the totals. Resolve each conflict in the DynamoDB schema design and merge again before migration.

## DynamoDB merge-review decisions

When two or more DynamoDB design groups each give the same source table its own home, the merge keeps one table as the authoritative home, which takes every write to that source table, and the others as derived copies, updated from the home's DynamoDB Streams. It chooses the home by the statements its access patterns serve, then their design RPS. It records the choice, so every deliverable states the home it chose; for a design merged before it recorded it, the deliverables say the choice was reconstructed from the design's access patterns, and merging again records it. The engineering report and the results page list each decision under "DynamoDB merge-review decisions": the source tables, the authoritative home, the derived copies and the data-consistency risk the overlap leaves. The executive report states the totals and the same review sentence on its Decisions needed page, without naming a table. Review each choice before migration: reads on a derived copy are eventually consistent.

## Design trade-offs

Each schema design records its trade-offs, and each trade-off carries a topic the designer picks: item and value size, generated IDs, indexes, keys and data layout, query translation, consistency and freshness, uniqueness and conditional writes, data types, capacity and hot keys, cost, operations, or other. What the assessment adds of its own is filed apart: the design review's notes under design review notes, and the schema design's own warnings (a revision that failed, a design salvaged from partial output) under design warnings, next to the design's trade-offs. The engineering report's "Migration trade-offs" section and the results page's "Trade-offs and design decisions" tabs list each engine's trade-offs under their topic with its count, so a limit several design groups each state (the 400 KB item limit, say) reads as one group. A design saved before topics existed lists its trade-offs as before, with its review notes and warnings apart.

## Costs

Every cost figure is labelled as the full-modernization estimate: all waves done, every kept engine running. It is not the cost of wave 1. The estimates use public on-demand list prices for the stated Region, and the TCO lists its assumptions; check them with your own pricing in the [AWS Pricing Calculator](https://calculator.aws/). With no current cost collected for the source, the deliverables say so and claim no saving. When the DynamoDB design keeps derived copies of data in sync through DynamoDB Streams, the deliverables price that sync, list it under the overlap risk it belongs to, and count it in the DynamoDB cost, with the TCO stating what the figure includes. Once a DynamoDB design exists, the DynamoDB cost also counts its global secondary indexes (their storage and the extra write each base-table write takes on them), and the TCO states that share. Call rates, and the sizing and costs built on them, come from the collection's two snapshots of the counters when it took them (the change in each count over the time between them, 300 seconds by default, #1908); otherwise they divide each statement's execution count by the window it covers: its own window (for most engines the time it was active), else the server's window, else an assumed 24 hours. ## Risks

The engineering report carries the risk posture (the overall risk is the highest severity among the open risks), a risk register of the open risks by engine, each with its mitigation and the tables it affects, the risks the assignment already resolved, and the mitigation strategies, which name each risk by its id (the register states its mitigation once) and give the checks after each wave. Each wave's gate in the migration roadmap lists the risks to close before it, and a risk due at that gate points to it. The executive report's Risks page gives the same open risks without table names. Risks cover anything the deterministic scoring flagged as low-fit, the reads that run on a replica, close calls, schema design that was not run, and any assumption the model made that depends on data this tool couldn't see (traffic patterns, peak load, compliance requirements). Read them before treating the migration roadmap as a commitment.
