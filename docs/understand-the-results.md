# Understand the results

This describes the deliverables the pipeline produces today.

## The pipeline, in plain terms

1. **Collect** parses the source database's schema and query patterns.
2. **Triage** looks at workload signals (key-value lookups, text search, time-series, etc.). Every engine that can own a query is analyzed and scored; the signals are evidence for an engine, not a filter. The ElastiCache cache layer, which owns no query, is analyzed only when one of its signals fires.
3. **Analyze** scores every query against each engine triage selected, deterministically.
4. **Assign** routes each query to its best-scoring engine. Co-dependent queries (joins across the same tables) move together, and all of a table's writes land on one engine, the table's source of truth; another engine can still serve the table's reads from a copy kept current by CDC.
5. **Reality Check** removes an engine once the engines that remain can serve its queries just as well, and moves each of its queries onto its own best-fit remaining engine. A model's flag on a moved query re-routes it only among the engines that remain; it never brings a removed engine back. <!-- claim: tests/unit/agents/referee/test_reality_check_request.py::TestAFlagOnWordpressNeverBringsBackDocumentDB::test_one_flag_goes_to_the_best_kept_engine, tests/unit/agents/referee/test_reality_check_llm_seam.py::TestApplyLlmOutputHandlesCorrectionsAndSummary::test_a_flag_never_brings_back_the_removed_engine --> The source-compatible Aurora engine survives this consolidation unless another engine scores better, or is at least 40% and $100/month cheaper. <!-- claim: tests/unit/agents/referee/test_source_compatible_tie_survival.py::TestTheIssueRepro, tests/unit/agents/referee/test_source_compatible_tie_survival.py::TestANonTieIsUnaffected, tests/unit/agents/referee/test_source_compatible_tie_survival.py::TestTheCostException --> A model can check that each move still works; the consolidation itself is deterministic and does not need it.
6. **Routine checks** run after Reality Check, when the collection holds routines: each PostgreSQL, MySQL or MariaDB routine is checked against its Aurora target and rewritten where a safe rewrite exists, with no model (see [Routines](#routines)).
7. **Schema Design** produces concrete schemas per engine: DynamoDB table definitions, DocumentDB collections, OpenSearch mappings, the relational DDL that stays.
8. **Routine repair** asks a model to repair the routines the checks could not carry, for at most 3 rounds; a repair is carried only once a side-by-side comparison with the original accepts it.
9. **Synthesis** produces the final report: ranking, TCO, the migration roadmap, risks, and an executive summary. A wave held for a reason its design can fix goes back to Schema Design for at most two rounds (see [Migration waves](#migration-waves)).

Collect through Reality Check, and the routine checks, never need a model. Schema Design, Routine repair and the Synthesis executive summary do. Testing the carried routines and moving the data come after the assessment, with `/test-routines` and `/move` (see [After the assessment](use-claude-code.md#after-the-assessment)).

## How to read an assignment

Assignments map **queries** to engines, not tables. Several engines can serve the same table. The deliverables state one line per source table, computed from the final assignment:

- **Owner**: the same owner the migration waves name. It is the engine that takes the table's writes (a table has one writer). A table no query writes stays on the plan's relational engine, whichever engines read it, and they read a copy; with no relational engine in the plan it stays on the source database. <!-- claim: tests/unit/agents/referee/test_unwritten_table_owner.py::test_a_table_several_engines_read_stays_with_the_relational_step, tests/unit/agents/referee/test_unwritten_table_owner.py::test_with_no_relational_step_the_source_database_keeps_it --> When a table's writes still sit on more than one engine, the map says "no single writer" next to the owner the waves name, and Sources of truth lists the table with no source of truth. A cache or search engine never owns a table, so a table the cache design keys still has its system-of-record owner and counts where that owner's tables count.
- **Also read by**: every other engine whose queries read the table. It reads a copy kept current from the owner via CDC. The results page names this column CDC to.
- **Cached by**: the cache in front of the table's reads (ElastiCache), when one is.

The "recommended engine" in a `table_mappings` entry is the schema design that maps the table with the highest fit; it does not make that engine the owner. Each entry also carries `owner`, `owner_basis`, `also_read_by` and `cached_by`, and `facts.table_owner_lines` has the same lines and their counts. Each engine's confidence score is the mean fit of the queries actually routed to it, not every table it was evaluated against; a score with no table-level evidence behind it is labelled "signal only."

## The cache layer

ElastiCache is recommended only for hot reads, as a cache-aside layer in front of each cached read's owner engine. This is the tool's recommendation, not a limit of the service: the cached reads are hot, small and can be rebuilt from their owner, so the owner (Aurora, DynamoDB or DocumentDB) stays the system of record and the cache is sized for the hot reads, not the whole dataset. In the plan the cache never owns a query, and if it is lost the owner still has every row. [ElastiCache for Valkey 9.0 and later offers durability](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/durability.html) on Multi-AZ clusters, with synchronous or asynchronous writes; the tool does not use it as a system of record today. Every deliverable states this recommendation in the same sentence, from `facts.cache_layer.role_sentence`. <!-- claim: tests/unit/agents/referee/test_elasticache_never_owns_a_query.py::test_the_ledger_refuses_a_first_move_onto_a_cache, tests/unit/agents/referee/test_elasticache_never_owns_a_query.py::test_the_ledger_refuses_moving_an_owned_query_onto_a_cache, tests/unit/agents/referee/test_elasticache_never_owns_a_query.py::test_the_ledger_refuses_a_tie_that_names_a_cache, tests/unit/agents/referee/test_only_the_ledger_writes_engines.py::test_only_the_move_ledger_writes_engines_and_ties, tests/unit/agents/referee/test_elasticache_never_owns_a_query.py::test_every_table_a_cache_fronts_has_a_system_of_record_owner, tests/e2e/test_elasticache_never_owns.py::test_no_saved_assignment_or_report_lets_a_cache_own_a_query, tests/e2e/test_elasticache_never_owns.py::test_every_table_a_cache_fronts_keeps_a_system_of_record_owner, tests/unit/report/test_cache_role_sentence.py::test_every_deliverable_states_it_once, tests/unit/report/test_cache_role_sentence.py::test_every_deliverable_reads_the_stored_fact -->

## OpenSearch as a read model

OpenSearch serves search and analytics queries, but every table it serves keeps a durable owner elsewhere. OpenSearch is kept current from that owner and never holds the only copy. If the index is lost, you re-index; no data is lost.

## Migration waves

The deliverables lay out a suggested step-by-step path that starts with the relational move. For example: Wave 1 moves the source database to Aurora with no data model changes yet; Wave 2 adds a cache layer in front of the hot reads; Wave 3 moves key-value queries to DynamoDB; Wave 4 adds OpenSearch as a read model for search and analytics queries. The fully decomposed target architecture appears next to it as the direct, single-step option. The wave order is a suggestion; other orders work too, and the end-state schema is the same either way.

Each wave lists every table its queries use, not only the tables its engine owns, and the engineering report shows both numbers as "N source tables (M to move)". The tables that move go to the wave's engine. The rest stay owned by their current engine (usually Aurora) and are kept current by CDC from that owner. In the Target engines table, each migration target's Scope cell splits its served tables the same way: how many migrate, how many move to another engine of the same wave, and how many are kept current by CDC. ## Sources of truth and replicas

All of a table's writes land on one engine, its source of truth. When another engine serves some of the table's reads, it reads a copy kept current from the source of truth via CDC, so those reads are eventually consistent. The engineering report lists each written table's source of truth, its replicas, the CDC direction and how many reads run on a replica; the results page has them as the Owner, CDC to and Replica reads columns of its Table owners table. The risk register carries the consistency risk.

## Close calls

A close call is a query whose engine scored less than 5 points above another engine the plan keeps, which could serve it too. The assessment still decides, deterministically; the engineering report and the results page list them so you can move any of them yourself in the assignment review. Exact ties a routing rule settled are counted apart from them.

## Unresolved DynamoDB merge conflicts

DynamoDB is designed in parallel query groups, and their designs are merged into one. When two groups design the same table differently and the merge cannot reconcile them, it keeps one design and fails validation. `/modernize` sends the conflict back to the designers, but a run with no fix round (`--llm-mode bedrock`) keeps it. The engineering report and the results page then list each conflict under "Access patterns the merged DynamoDB design does not serve": the failure, and the access patterns and queries it concerns. Patterns are **not served** when the merged design runs them on a table or index that was not designed for them (the dropped design's patterns, or a pattern on a table or index the design does not define). They are **at risk until the conflict is resolved** when they run on a table the failure concerns: one that cannot be created as designed (more global secondary indexes than the default limit, a name over 255 characters), the tables holding rows with contradictory keys, or rows the merge could keep no safe key for. A failure that names no access pattern says so. A design merged before the assessment recorded these lists says its unserved patterns were not recorded; merge it again to list them. The executive report states the totals. Resolve each conflict in the DynamoDB schema design and merge again before migration.

## DynamoDB merge-review decisions

When two or more DynamoDB design groups each give the same source table its own home, the merge keeps one table as the authoritative home, which takes every write to that source table, and the others as derived copies, updated from the home's DynamoDB Streams. It chooses the home by the statements its access patterns serve, then their design RPS. It records the choice, so every deliverable states the home it chose; for a design merged before it recorded it, the deliverables say the choice was reconstructed from the design's access patterns, and merging again records it. The engineering report and the results page list each decision under "DynamoDB merge-review decisions": the source tables, the authoritative home, the derived copies and the data-consistency risk the overlap leaves. Review each choice before migration: reads on a derived copy are eventually consistent.

## Risks

The engineering report carries the risk posture (the overall risk is the highest severity among the open risks), a risk register of the open risks by engine, each with its mitigation and the tables it affects, the risks the assignment already resolved, and the mitigation strategies, which name each risk by its id (the register states its mitigation once) and give the checks after each wave. Each wave's gate in the migration roadmap lists the risks to close before it, and a risk due at that gate points to it. The executive report's Risks page gives the same open risks without table names. Risks cover anything the deterministic scoring flagged as low-fit, the reads that run on a replica, close calls, schema design that was not run, and any assumption the model made that depends on data this tool couldn't see (traffic patterns, peak load, compliance requirements). Read them before treating the migration roadmap as a commitment.

## Routines

When the assessment collected routines (functions, procedures, triggers and events), every deliverable says how they migrate, from the same facts.
