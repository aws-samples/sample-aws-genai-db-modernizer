# ADR-034: Carrying Database Routines to Aurora

**Status:** Accepted (2026-11-06). The checks, the safe rewrites, the routines file and the disposable source engines are built; every other decision below is decided but not built yet, and names the issue that builds it. Epic #1925 implements it.
**Date:** 2026-11-06
**Deciders:** Database Modernizer Assessment Architecture Team
**Related ADRs:** ADR-031 (Query-First Routing and the Engine Rule Catalog), ADR-032 (One Facts Layer), ADR-033 (Data Movement Driven by a Transformation Contract)

---

## Context

Customers hesitate to modernize when their stored procedures, functions, triggers and events (here, *routines*) don't come along, because they expect to rewrite them by hand. The pipeline assesses where logic lives (epic #1657), but nothing carries it to the target. This ADR records how routines are carried to the target Aurora engine: in what order, how a routine is checked, repaired and tested side by side, where its exact text is kept, and how a routine that can't be carried shows up.

The collection is redacted: literals in collected SQL are replaced before anything reads them (#1625). A routine can't be deployed from redacted text, so carrying routines needs the exact `CREATE` statement, literals included, without weakening that rule.

## Decision

### 1. Order of work: same family first, then SQL Server, then Oracle

Routines are carried first between engines of the same family: PostgreSQL to Aurora PostgreSQL and MySQL to Aurora MySQL (epic #1925). SQL Server to Aurora PostgreSQL comes next, then Oracle to Aurora PostgreSQL; each adds a translation step between checking and carrying and reuses the rest. Routines moving into purpose-built engines (DynamoDB, ElastiCache, OpenSearch) come later. Neither the dialect translations nor the purpose-built targets have an issue yet; the epic files them when the same-family phase is done.

### 2. Carry over, deterministic first; model repair is an untrusted seam

A routine is carried over, not redesigned. Parsing, checks, safe rewrites, ordering and proof are deterministic code, with the rules as catalog data (ADR-031 Decision 8). Every routine ends with a verdict and a reason; none is dropped or guessed.

A model is used only to repair a routine the deterministic path could not carry (#1940, #1941, not built yet). Its answer is untrusted data, framed with `frame_untrusted`, and it follows the LLM seam pattern, so it runs in all three LLM modes and not at all with `--llm-mode none`. Each candidate goes back through every check and through the side-by-side test (Decision 5); only a candidate that passes both is carried. A routine gets at most 3 attempts, each fed the previous failure; after that it stays *needs attention*, with every attempt recorded. The model works on the redacted text and returns structural edits, which are applied to the exact text only when the routine has been tested and is deployed (Decision 4).

### 3. Default target: the Aurora line the assessment chooses; a newer line is an option

Routines are checked and tested against the Aurora version line the assessment already chooses for the move: the source's own major, unless an extension the source uses is offered only on a later Aurora PostgreSQL line (#1078). Moving to the newest Aurora line instead is meant to be the customer's option. Today it is a library parameter only: `routine_target_line(..., target_choice="newest")` returns the newest listed Aurora PostgreSQL line, and the same-major choice stays the default. <!-- claim: tests/unit/tools/routines/test_postgresql_version_change_checks.py::test_the_newest_line_is_an_option_and_same_major_stays_the_default --> No command, UI or pipeline caller lets the customer pick it yet, and the side-by-side test (Decision 5) does not run on the newer line yet; #2028 builds both. A newer line brings version-change checks between the two majors, each backed by the release notes through PostgreSQL 18: removed or renamed PostgreSQL functions, catalog columns, settings and types, and changed defaults that affect a routine (PostgreSQL 15's public schema, PostgreSQL 17's maintenance `search_path`); and for MySQL, the 5.7 to 8.0 and 8.0 to 8.4 reserved words, removals and `GROUP BY` sorting. <!-- claim: tests/unit/tools/routines/test_postgresql_version_change_checks.py::test_the_newest_line_brings_the_version_rules_the_default_line_does_not, tests/unit/tools/routines/test_postgresql_version_change_checks.py::test_each_rule_runs_only_from_a_source_older_than_its_line --> A version-change rule runs only when the move crosses its version: the source's line is older than it and the target line has it, so never on a same-major target, and its outcome is unknown, never a pass, when the source's version is unknown. <!-- claim: tests/unit/tools/routines/test_mysql_version_change_checks.py::test_rules_never_run_on_a_same_major_target, tests/unit/tools/routines/test_mysql_version_change_checks.py::test_the_version_change_scope, tests/unit/tools/routines/test_mysql_version_change_checks.py::test_an_unknown_source_version_leaves_the_rules_unknown_never_pass --> A MySQL 5.7 source has no same-major Aurora line, so its move always crosses 8.0 and the MySQL 5.7 to 8.0 rules run on every line (#1952). <!-- claim: tests/unit/tools/routines/test_mysql_version_change_checks.py::test_a_57_source_gets_the_rules_on_every_line -->

### 4. Two files: the collection stays redacted, a separate routines file holds the exact text

When the customer leaves routine bodies on (`include_routine_bodies`, on by default, #1933), the same collection run also writes a separate, optional routines file, `collector/routine_sources.json`, in compressed chunks, holding the exact `CREATE` of each routine, literals included (#1931, #1932). Every collection script, SQL Server's and Oracle's included, has the `include_routine_bodies` switch at its top, and a body the collecting user can't read is listed as `not_readable` with the reason, never failing the collection (#1933). <!-- claim: tests/unit/agents/test_routine_body_readability.py::test_the_sqlserver_script_has_the_switch_at_its_top_and_reads_readability, tests/unit/agents/test_routine_body_readability.py::test_the_oracle_script_has_the_switch_at_its_top, tests/unit/agents/test_routine_body_readability.py::test_a_sqlserver_body_the_user_cannot_read_is_not_readable_with_its_reason, tests/unit/agents/test_routine_body_readability.py::test_an_oracle_unit_with_no_source_lines_is_not_readable --> Each carried `CREATE` is checked by the repository's one credential scan, `src/shared/secret_scan.py`, which the CI private scan (`ci/llm/private_scan.py`) also uses. ### 7. A routine that can't be carried automatically is a to-do for the customer

*Amended (2026-11-10, maintainer decisions on #1938):* a routine the pipeline can't carry automatically (a failed check, a dependency problem, or code it could not read or check) is a HIGH migration risk that names what it touches, why and the next step, and it is a to-do for the customer: "we could not translate N routines automatically; migrate them yourself before wave N". It never holds a wave's readiness or suggestion: the wave's line lists the to-do, and the wave's gate in the roadmap lists it as a to-do ("To do before wave N: migrate N routines yourself (RISK-00N)"), not as a condition to close. When no wave brings in the routines' target, the texts give no timing and say only "migrate them yourself; the cutover is your responsibility". The step 1 move gate's routines check (`src/tools/data_movement/dms_gate.py`, Decision 6) is separate and unchanged: it still fails for a routine step 1 does not carry, named. A routine that runs but differs from the original is a MEDIUM risk that *behaves differently*, with the difference; a routine with no code to check because the customer turned body collection off is a MEDIUM information risk. The carried routines that were rewritten or have a check that could not run are one LOW risk with the counts. The tests listed for Decisions 2 to 5 guard the parts that are built (the checks, the rewrites, the routines file, the disposable engines and the side-by-side comparison); each `none yet` issue adds the guard for the rest.

## Consequences

- Customers get their routines carried with a verdict they can check, in exchange for a proof stage that needs a disposable source engine and a test target.
- The exact routine text lives in a second file, kept apart from the redacted collection; without it, routines are assessed but not carried.
- A routine the pipeline can't carry, or whose side-by-side test finds a difference or cannot compare it, is listed as a to-do in its wave's gate in the roadmap (Decision 7), rather than being left to surface after the move. The cutover is your responsibility.
- Model repair can never carry a routine on its own: a candidate that fails a check or the proof is not carried.
- Moving to a newer Aurora line costs more checks and a proof on that line, so it is opt-in.

## Alternatives considered

- **Report incompatibilities and rewrite nothing.** Rejected: it leaves every fixable routine to the customer.
- **Accept a model's first candidate.** Rejected: nothing a model writes reaches the customer's schema unchecked (ADR-033 Decision 6).
- **Keep the exact routine text in the main collection.** Rejected: the collection and every deliverable stay redacted (#1625).
- **Check only that routines load.** Rejected: loading shows nothing about behaviour.
- **Enable triggers at deploy.** Rejected: DMS already applies the source triggers' effects during replication, so they would apply twice.
- **Ask customers for a schema dump with routines.** Rejected: it works, but it isn't hands-free.
