# ADR-032: One Facts Layer in Synthesis; Renderers Only Format

**Status:** Accepted
**Date:** 2026-10-14
**Deciders:** Database Modernizer Assessment Architecture Team

> **Amended (2026-10-17, #1020):** the multi-page PDF report was retired. Its "Queries moved" total is a fact (`facts.moving_query_count` of `facts.in_scope_query_count`, contract 1.28), and so are the resolved risks by severity it and the engineering report print (`facts.resolved_risks_by_severity`), and its architecture bar is the one pinned presentation exemption (chart geometry). ## Context

Every deliverable (the decision report, the engineering report, the executive summary PDF, and the interactive analysis report the UI exports) renders one synthesis `report.json`. AGENTS.md's "Deliverables agree" invariant says a fact changed in one must change in all. In practice each deliverable computed its own figures from the raw fields, and the copies drifted:

- the merged DynamoDB/DocumentDB wave headline subtracted the deduped `table_owners` list from `table_count`, while the "Tables migrate" tile summed `owned_counts_by_engine`, so the two disagreed whenever one engine of the wave served a table the other owned (#581);
- the old executive deck's "Basis of the analysis" bullet took a partial `table_mappings` as the complete, fit-scored table count, while the tile added the migration-wave fallback of the engines with no schema design yet (#533);
- wave 1 stated 312 "source tables and views" next to "Analyzed 311 source tables", with nothing saying the extra one is a real view (#578);
- earlier, the deck truncation and the "400 tables migrate" out of 311 double count (#568), and three copies of the eliminated-engine rule (#235).

The deliverable-consistency e2e test (#573) catches such a disagreement after it happens; it does not remove the reason the copies exist.

## Decision

### 1. Synthesis computes every customer-facing figure once, into `report.json`

`src/shared/report_facts.py` (`compute_report_facts`) computes the figures the deliverables print: each engine's role, workload, cached reads, source tables, tables that migrate and monthly cost; the totals (engines, tables migrate, workload, cost, the projected monthly cost); the table basis behind "N tables mapped" with its design coverage; each wave's served, moving and kept-in-sync tables and wave 1's tables and views; the no-migration step's figures; the open and resolved risk counts by severity, type and engine; the tied-query count. Synthesis writes the result to `report.json` as `facts` (`SynthesisOutputContract.facts`, `ReportFacts`, contract 1.14). A new figure a deliverable needs is added here first.

### 2. Renderers only format

The modules under `src/report/` read figures through `src.report.facts.report_facts` and format them: they never count, total, add, subtract or filter a figure the facts layer owns. The owned figures are every numeric, record and record-list field of the `ReportFacts` contract (derived from the model, so a new fact is owned when it is added) plus the `report.json` inputs they are computed from. A sum of percentages is stored unrounded, so each renderer rounds it once, to the places it prints. Counting what a list shows ("+N more" after the first 20 names) is formatting; a line that computes on a fact for presentation only (chart geometry, verb agreement) says so with `# facts: presentation (<reason>)`, and the exemptions in use are pinned in the guard test. The legacy wave builder (`src/report/waves.py`, for a report synthesized before `migration_waves` existed) produces data, not output.

The JavaScript side follows the same rule (#748). `src/ui/src/utils/__tests__/rendererOnlyFormat.test.js` parses the UI sources that read `report.json` (the results page and its components and the helpers they use), and fails when one counts, totals or does arithmetic on an owned figure (`.length`/`.size` of a fact list, `reduce`, `Math.max`, arithmetic, an accumulator inside a loop over a fact). It is a jest test over a real parse (`@babel/parser`, shipped with react-scripts) because Python has no JavaScript parser and a text search cannot follow `const risks = ra.risks.filter(...)` to a later `risks.length`. An emptiness check (`xs.length > 0`) shows no figure and is allowed; `// facts: presentation (<reason>)` and a pinned exemption list work as in Python (empty today). The owned keys are read from the contract snapshot (`tests/contract/schema_snapshot.json`), so a new fact is owned the moment it joins `ReportFacts`.

### 3. Layering

`src/report/` imports nothing from `src/agents/`; the facts layer imports neither `src/agents/` nor `src/report/`. The layer lives in `src/shared/` so synthesis can write it and the renderers can compute the same block for an old report, from one implementation.

### 4. One reader, one answer for an old report

`report_facts(report)` returns the stored `facts`, and for a report synthesized before they existed computes them with the same `compute_report_facts`, over the waves `resolve_migration_waves` resolves for it. The `/results` API (`src/api/routes/results.py`) always carries `facts`, filling them in with the same function for an older report; the UI reads them through `src/ui/src/utils/reportFacts.js` and only formats them.

### 5. The consistency test stays underneath

`tests/e2e/test_deliverable_figures.py` keeps reading every deliverable's figures back and comparing them with `report.json`, and also checks that the stored `facts` are exactly what the layer computes from the report's own fields.

### 6. Labels and reasons are facts too

A deliverable never reads a decision back out of prose. The triage signals that overrode queries onto an engine are `facts.engines[].signal_overrides`, from the assignment's own `signal_override` fields; the reason text itself names the signal and the engine by their readable forms (#584). The engines the reality check removed are `facts.removed_engines`, judged against the final architecture of the effective assignment, so an engine a customer edit moved queries back onto is never listed; a reality-check consolidation line that edit reversed is `reversed` in `facts.reality_check_trade_offs` and no deliverable states it as current (#546). This is decided per query (#861): synthesis records, for each consolidation, the queries it moved and those the effective assignment has put back on the engine they left; a line is reversed when every query it moved is back, and a line an edit undid only in part is restated once, in `description_now`, for what stayed moved, which every deliverable shows instead of the check's original line. A partial consolidation, or an engine a customer pin keeps, with nothing moved back is current as written. The reality check's own consolidation lines are parsed once, in the facts layer, never by a renderer. The per-query decision traces (#339) follow the same split: synthesis writes them into `report.json` as `query_traces` (only the queries that moved after their first assignment, were tied at some step, were overridden or were pinned by a listed rule, at most `TRACE_FULL_CAP` of them with their full trace; the rest counted by their first rule), built by `src/shared/query_trace.py`, the builder the graph's trace API uses too; `facts.query_trace` holds their figures and which queries are listed and why, and the traceability appendix of the engineering report only formats them (the executive report shows no trace, #1020). The Python guard owns every field read off `query_traces` at any depth, so a renderer cannot recount the listed traces. The close calls (#730) follow it too: synthesis records in `query_traces.close_calls` every query whose trace runner-up, an engine the plan keeps that can take it, is less than `report_facts.CLOSE_CALL_MARGIN` points behind its final engine (selected with `report_facts.is_close_call`), and `facts.close_calls` groups them by engine and alternative; the engineering report's table and the UI results page's callout only format them (the executive report leaves them out, #1020), the exact ties a rule settled counted apart from the close calls. The queries on a fallback engine (#729) follow it as well: `query_traces.unservable` records every query whose deciding step is a fallback rule or has every candidate engine gated (`report_facts.is_unservable`), with where it landed, each engine's gate and the capabilities triage found it needs, and `facts.unservable` adds a redesign hint for the engines that ruled it out (`capability_labels.redesign_hints`); the engineering report, the executive report (under "Decisions needed") and the UI results page state them with the assignment review as the way to re-run, and no removed engine comes back. Each written table's source of truth and replicas (#992, ADR-031 Amendment 9) follow it as well: synthesis writes `table_sources` from the assignment's write groups, `facts.table_sources` adds per replicated table its replica engines and the eventual-consistency risk naming the reads a replica serves, and the engineering report's wave plan and the UI results page only format them (the executive report names no table, #1020). The flagged queries no kept engine can take (#888), which never reach the move ledger (a reality-check model flag whose outcome is `kept`, a post-schema router terminal query), are recorded by synthesis in `flagged_unservable` (`src/agents/referee/flagged_unservable.py`) while the effective assignment keeps them in scope on the flagged engine, and `facts.unservable` states them as a third kind, `flagged`, with the reason category's redesign hint (`capability_labels.flag_redesign_hints`); a query the decision trace already lists keeps that row. The engineering report, the executive report and the UI results page format both kinds in one section, "Queries that cannot be served as designed", whose sentences and JSON pointer follow the kinds it lists (`facts.unservable.no_fit_query_count`, `flagged_query_count`), so a flagged query is never described as a fallback.

### 7. Every deliverable shows the reality-check decisions

The reality check's own trade-offs that still apply (the engines it consolidated, the engines its sanity sweep kept, the patterns it recommends) are `facts.reality_check_decisions`, each with its kind, engine, title and detail. The executive report lists them under "Reality-check decisions" on its "Why this architecture" page, the engineering report keeps its "Migration trade-offs" section, and the UI's results page lists them in a "Reality check" trade-offs tab (#595).

## Consequences

- A deliverable can no longer disagree with another on a figure the facts layer owns: both print the same field. The renderers lose their own arithmetic (`architecture._architecture_engines` and the wave headline are formatters over facts now).
- `report.json` grows by the facts block (a few kilobytes on the discourse sample).
- A new deliverable, or a new figure in an existing one, starts by adding the figure to `compute_report_facts` and its contract model; the guard test fails if a renderer computes it instead.
