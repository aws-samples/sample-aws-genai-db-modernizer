# ADR-031: Query-First Routing Model and Engine Rule Catalog

**Status:** Accepted **Date:** 2026-10-11 **Deciders:** Database Modernizer Assessment Architecture Team **Related ADRs:** ADR-017 (Analysis Agent Scoring Framework), ADR-018 (Reality Check and Human Approval Gate), ADR-021 (Aurora Absorption Pass in Reality Check), ADR-026 (Fold Reality Check into the Assessment Core)

---

## Context

The routing model has been described across many issue threads rather than one document: how a query gets its engine, how the reality check consolidates engines, how co-dependency groups move, how cost factors into scoring, and how pattern-and-engine rules should be organized. Contributors and reviewers have had no single place to read the intended model or check a routing change against it.

An audit of the routing code against that intended model found that the model itself needed decisions, not just a write-up: whether cost is really a dimension of the score, how DynamoDB's transaction support should be scored, and how pattern and engine rules should be organized so one fact is not encoded in several places that can disagree. This ADR records those decisions. It does not record the audit's measurements, which belong to the tracking issues the audit filed.

Earlier ADRs described parts of this model before these decisions were made. ADR-017 introduced per-query scoring and per-target weights but predates engine-neutral detection and a declared cost dimension. ADR-018 introduced the reality check as engine consolidation, with its own capability and scoring logic separate from the resolver's. ADR-021 added an Aurora-specific absorption pass with its own fitness gate, inside the reality check. ADR-026 folded the reality check into the assessment core without changing how it scores a query. None of them described the query as the sole unit of assignment, a single engine- and query-aware cost dimension, or a pattern-first, engine-neutral rule catalog.

## Decisions

### 1. The query is the unit of assignment

Every routing decision is made per query. A table is an input to a query's score; it never decides a query's engine on its own. The engine recommended for a table in a table-level mapping is a summary, not ownership. No step may assign a query because of what other queries on the same table do: no table majority, no table owner, no table-wide classification. Counts, summaries and groups shown in deliverables are built from queries; a query group reported for a relational engine is a real group of queries, not a stand-in for a table.

**Amendment 9 (2026-10-17, maintainer decision, #992): a table has one writer; its reads stay per query.** Every statement that writes a table (an `INSERT`, `REPLACE`, `UPDATE`, `DELETE` or `MERGE`, a data-modifying CTE's included) and every locking read on it (the `locking_clause` of Decision 2 step 3) lands on one engine, the table's source of truth. Its reads stay per query: another engine may serve a read as an eventually consistent replica, fed by change data capture (CDC) from the source of truth. That is CQRS, for example writing to DynamoDB to take heavy traffic off Aurora and replicating to Aurora for aggregations, multi-column filters, joins or analytics. This rule is narrower than the table-owner rule this decision forbids, in three ways: it groups a table's writes only, never its reads; the group's engine comes from its members' own per-query scores, never from what the table's reads prefer, a table majority or a table-level classification; and a read moves because of a write group in one case only. When a JOIN co-dependency group (Decision 4) contains a write of the table, the two must place as one unit, or one of them would split: the JOIN group's reads are then placed with the table's writes, on the merged unit's mean, and can move with them (their Moves keep the co-dependency rule `group.mean`; the writes take `group.write`). A read in no such JOIN group never moves because of a write group, and a co-dependency group that shares no statement with a write group is placed exactly as before. On the bundled samples this happens in discourse only: its 189-query JOIN group shares writes with 15 tables' write groups (one 258-query unit, 91 of them reads), and a 2-query JOIN group with one table's (a 3-query unit); none of those reads changes engine.

A table's writes are the targets the shared SQL facts read in the source's dialect (`QueryFacts.write_targets`, the facade's `SqlFacts.write_targets` with its regex fallback, Decision 8): every table a MySQL multi-table `UPDATE a JOIN b ... SET a.x = ?, b.y = ?` (or `UPDATE a, b SET ...`) names in its `SET`, never a table a write only reads (the source of an `INSERT ... SELECT`, an `UPDATE ... FROM` table, a `MERGE`'s `USING` source). A locking read writes every table it reads, since it locks their rows; a write whose target the facts cannot read counts as writing all its tables, since keeping too many writes together never splits one table's writes; an administration statement (`TRUNCATE`, DDL) joins no group, since the utility pin places it. `write_groups.build_write_groups` builds each table's write group, and the assignment stores it (`Assignment.write_groups`).

How the code applies it. A write group of two or more statements is placed by Decision 4 Amendment 4's rule with one change, its weighting (maintainer decision, 2026-10-17): only an engine that can serve and own every member is a candidate (so an engine that is not a system of record never is), and the group's score is the call-rate-weighted mean of its members' own scores from the shared scorer (`co_dependency.group_engine_scores` with `write_groups.unit_call_weights`, no private fit function), so a rare write cannot drag a table's frequent writes off the engine that serves them best. Each member weighs its collected call rate (`calls_per_second`) over the unit's busiest member's, so the busiest weighs 1.0 and equal rates weigh exactly 1.0 each, the plain mean. Any member below `write_groups.CALL_WEIGHT_FLOOR_SHARE` (1%) of the busiest member's rate, one with no recorded calls included, weighs that 1%, so it counts but never vanishes. A unit with no call statistics at all takes the plain mean. On the bundled samples the floor binds one write (trailgear's UserSession DELETE), and every result is the same for any floor from 1e-9 to 0.05, a margin of 5 to 7 times over the 1% used (the first flips are discourse `users` at about 5.5% and `user_actions` at about 7.5%). A group's score is rounded to `co_dependency.GROUP_SCORE_PLACES` (6) decimal places before any comparison, so float noise in a weighted mean never decides between two engines: equal to that precision is an exact tie, for `tie_break`. A merged unit (below) is weighted the same way, over all its members. A co-dependency group no write group touches keeps Amendment 4's plain mean. The weights travel with the unit to every pass (the routing trace's group entry, `write_groups.assignment_unit_weights`), so each pass judges the unit on the same number. An exact tie goes through `tie_break` (Decisions 2 and 12), with no engine preference. A write group and a co-dependency group that share a statement must move together, or one of them would split, so every pass places the merged units (`write_groups.placement_groups`; a co-dependency group no write group touches comes back unchanged): the first assignment (rule `group.write` for a unit holding a write group), the reality check (Phases 1 and 2 and the floors read the resolver's units from its routing trace; the sanity sweep and a model's flag take `write_groups.assignment_placement_groups`), the customer gate and the post-schema reroute (a flagged unit whose write group holds a customer-pinned write stays on the pinned engine, the flag a note on it, `RouterOutput.held_queries`, since the pinned write never moves; `RouterOutput.held` keeps each held query's flag, and the deliverables list it as an unservable query whose cause is the pin, #1033). Every engine change this causes is a Move (Decision 10 Amendment 3). At the customer gate, a pick of one write pulls the table's other in-scope writes with it (rule `group.write_customer_propagation`), and, when every pick in its unit names the same engine, the co-dependency groups they belong to; when the customer splits a unit's JOIN group across engines, each picked write still pulls its table's writes, and the JOIN split is left to the feasibility review; the edit is rejected, with the reason and nothing written, when another write of the table cannot make the move (it fails a gate a direct pick would fail) or when two writes of one table are picked onto different engines in one edit. A pick of a read in no JOIN group moves only the read; a pick of a read in a JOIN group moves that group's whole placement unit, so when the JOIN group shares a write with a table's write group, the pick also moves that table's writes (on discourse, a pick of any read in the 189-query JOIN group moves the writes of 15 tables with it). Each moved write says it moved with its table's writes (rule `group.write_customer_propagation`), each other member with its JOIN group (`group.customer_propagation`), and the edit's response lists every query the pick moved. A version saved before this rule can still split a table's writes. It is re-routed before the customer is shown it (the ATX review tools and the API's read, which the UI uses), and again wherever it could still reach (the ATX approval, the API's edit, and, after approval, the orchestrator's and the script's schema design): `assignment_overrides.reroute_split_writes` re-routes each unit holding a split table's writes to the kept engine with the best weighted mean (or the engine a customer pinned one of its writes to), each change a Move (rule `group.write_reroute`, its reason saying the write was re-routed to one source of truth), and writes a new version (`source = source_of_truth_reroute`, never an overwrite of an earlier version; a run that finds it already written by a concurrent run returns that version), so the changed engines' designs and the synthesis are stale and run again, as after a customer edit. After approval the version is marked `rerouted_after_approval` and each move is listed in `post_schema_reroutes` (cause `source_of_truth`), so every deliverable states what moved after the customer approved. A submission is compared against the version the customer was shown (the ATX gate diffs it against that version and applies only what they changed; the API refuses an edit made on an older version with 409), so an unchanged submission never becomes an override. Customer pins on two engines in one unit name no one engine: the unit is re-routed by score, each pin the move overrides is cleared, and the conflict is stated in the version's warnings. The feasibility review flags a table still written on more than one engine as blocking (`write_split`) and a replica as advisory, naming the source of truth, the replicas, the CDC direction and the reads a replica serves. The deliverables state each written table's source of truth (`TableAssignment.source_of_truth`, which the wave plan names as the table's owner instead of the plurality `primary_engine`), its replicas, the CDC direction and the eventual-consistency risk naming the replica-served reads (`report.json`'s `table_sources` and `facts.table_sources`, ADR-032).

### 2. A query's engine is decided in a fixed order

For each query and each candidate engine, the same five steps run in order:

1. **Candidates.** Every modeled target engine, minus any engine the source makes impossible. A homogeneous source always has its matching relational engine as a candidate. A heterogeneous source has exactly one relational engine as a candidate, chosen deterministically with the choice traced (see Decision 6). Triage selects every candidate for analysis whether or not a signal names it; its signals are evidence for the score, not a gate (#726). The cache overlay (ElastiCache) owns no query and so is not a candidate here: triage still selects it only when one of its own signals fires.
2. **Capability gate.** An engine is excluded only if it is structurally unable to run the query at all. Poor fit is a score difference, not an exclusion, and every candidate is held to the same gate.
3. **Ownership gate.** An engine that is not a system of record cannot own a write or a locking read. A locking read is one that `query_shape.locking_clause` finds (#838), the same detector the shape check records (Decision 14): `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`, MySQL `LOCK IN SHARE MODE` or a SQL Server `UPDLOCK` / `HOLDLOCK` / `XLOCK` / `SERIALIZABLE` hint, never a lock word in a comment, a string literal or a quoted identifier. The UI engine picker runs a JavaScript copy held to the same cases.
4. **Score.** A weighted average of four dimensions — pattern match, complexity, performance and cost — computed from the query's own tables and its own matched pattern signals, with the cost dimension the query's own cost on the engine (Decision 5). A table-level classification may inform a query only through that query's own matched patterns, never by inheritance from the table.
5. **Penalties.** A penalty applies only to an engine that actually lacks the capability a pattern needs (see Decision 3). An engine that runs a pattern natively is not penalized for it. Being able to run a query is not the same as having that capability: an unindexed substring match (a `LIKE` whose literal pattern starts with `%`) is its own pattern, `substring-match`, whose capability is a substring index. Aurora PostgreSQL has one (`pg_trgm`, an extension to create) and OpenSearch serves the match natively; Aurora MySQL and DocumentDB run the query but only as a scan of every row, so they lack it. A penalty for lacking a capability may also be conditional on the query: theirs applies only when the scan matters, a frequent query on a large table (the pattern's `scan_threshold`). A word search (`'%word%'` on a text column) is not penalized; each engine's redesign for it is stated as guidance (#493). A regular expression (`REGEXP`, `~`, `~*`, `SIMILAR TO`) is the same scan on an engine with no index for it, priced by the same rule, threshold and penalty (#982): Aurora PostgreSQL (`pg_trgm` serves `~` and `~*`) and OpenSearch are native, Aurora MySQL and DocumentDB scan. DocumentDB's entry is exempt (`prefix_regex_index`) for a query whose only scan is a prefix regular expression (the `prefix_regex` fact: a case-sensitive, non-negated `~` of a literal that always starts with at least one literal character, with no top-level alternation), which its index serves; Aurora MySQL's `REGEXP` uses no index, anchored or not. The scan is sized by the largest table the query reads, since the facts trace no column for a regular expression (#1098).

The highest total score wins. On an exact tie, the source-compatible relational engine wins; no other engine preference exists. In the reality check, where a query already has a current engine (the first assignment has none), a tie that includes that current engine stays there instead: a tie is not a strictly higher score for some other engine, so moving the query would add a migration cost for no score benefit at all. This stability rule only ever applies when exactly one tied engine is the query's current one -- two different, still-tied current engines (members of the same co-dependency group sitting on two different engines) is not "the" current engine either way, and is reported as unresolved, not decided by which one sorts first. When neither the source-compatible rule nor stability resolves a tie, Decision 12 governs the placeholder pending the customer's own choice. Decision 13 applies the source-compatible rule to the reality check's choice of which engine to remove, including when the source-compatible engine scores higher by less than the unique-value margin.

Two second-level decisions apply after the per-query result: co-dependency grouping (Decision 4) and a small set of listed overrides for database administration statements and justified search pinning, which skip steps 3 to 5 under a stated condition only.

### 3. DynamoDB supports ACID transactions; the score reflects shape, not a missing capability

DynamoDB supports ACID transactions: `TransactWriteItems` and `TransactGetItems` give atomic, consistent behavior across up to 100 items, and a conditional write is itself ACID on a single item. A transaction is therefore not treated as a capability DynamoDB lacks. The score instead reflects how far the transaction's shape is from that native support: a transaction touching one or a few entities scores well, a wide multi-table transaction on a normalized model scores poorly because it needs a redesign. The decision trace states which shape a query matched and why.

This supersedes any treatment that scores DynamoDB transactions as a missing capability requiring a saga or workaround, in favor of the shape-based score above.

How the code applies it (#493): one engine-neutral fact, `transaction_shape.transaction_shape` (`src/agents/referee/transaction_shape.py`), classifies every write as a single item, bounded (at most 100 items, `TRANSACTION_MAX_ITEMS`), key scoped, or unbounded (more items, or a set the statement does not bound: the rows an `INSERT ... SELECT` copies, or the rows a range, join, subquery or a filter with no key anchor picks). With the collected schema's keys (#915), a write is a single item or bounded only by a full primary or unique key (an `OR` of full-key values counts its branches). A write whose filter pins a key anchor but no full key (the #728 key-column rule, `TableKeys.key_columns`: a foreign key, an index's leading column, part of a unique key; `DELETE ... WHERE user_id = $1`) is key scoped: on DynamoDB that column becomes the partition key of an item collection (or a GSI's), and the write is a `Query` plus a batch write. It takes no penalty, and its trace records that schema-design requirement (`schema_note`) (maintainer decision on #915). A filter with no key anchor at all (`has_messages = $2`) is unbounded. A target with no collected keys (a view) keeps the text check's answer. The item count is the collector's measured rows per call when there is one, otherwise the statement's own `VALUES` rows or key values. DynamoDB is `native` for the `acid_transactions` capability and has `multi_doc_acid` in the hard gate, so no transaction excludes it or costs it the old flat redesign penalty. Only an unbounded write is DynamoDB's `wide-transaction` anti-pattern (`src/catalog/patterns/wide-transaction.toml`, 10 points, the reduced penalty DynamoDB transactions already carried, now applied only to the shape that needs the redesign). DynamoDB's decision trace records each write's shape, item count, reason and, for a key-scoped write, its schema note (`query_matches[].transaction_shape`).

### 4. Co-dependency groups move as one unit

Queries that must move together — statements in one transaction, or reads that must stay consistent with a write — are placed as one unit once the group's engine is decided. Every member goes to that engine, even if a member alone would score higher elsewhere; each member's own best engine is still recorded in the trace. How the group's engine is chosen — for example, from the members' combined scores — is not decided by this ADR and remains open, to be settled with options when the grouping code next changes (decided by Amendment 4, below).

**Amendment 4 (2026-10-14, maintainer decision, #727): a group goes to the best engine that can serve every member.** Only an engine that can serve every member of the group is a candidate for it: it passes every member's hard and capability gates and may own every member (and, in the reality check, passes the same eligibility rule a lone query moved there would pass). Among those engines, the group's score is the mean of its members' own scores from the shared scorer, and an exact tie goes through the usual tie-break (Decisions 2 and 12). An engine that strands one member is never a candidate, however well it scores for the rest; when no engine can serve every member, the group falls back as Decision 2 describes. One helper, `co_dependency.group_engine_scores`, applies the every-member test and the mean, and each pass that places a group supplies its own per-member eligibility test to it: the first assignment, the reality check, the sanity sweep, a model's flag and the post-schema reroute. In the reality check, Phase 1's removal check (whether an engine earns its place, and which removal loses least), Phase 2's placement and the justification floor all judge a group on the same numbers, from one helper (`reality_check_rules._moving_group_scores`, #894): the mean over the members that move with the group, from the resolver's per-query scores, rounded as the routing trace records a group's mean (Decision 7). A member that stays put is left out of that mean and of the every-member test: a mandatory signal override in Phase 1 and 2 (the floor moves those too), and a customer-pinned query, which the check never moves. In the floor a tied member counts every tied engine as current, as Decision 12 says. In Phase 1, an engine that cannot serve every moving member holds no group score, so the member is redundant there and adds no score difference; it is also left out of Decision 13's every-query check, so a query the engine cannot keep as one unit never costs the source-compatible engine its protection. The group stays together on one engine unless it can be decoupled with the same behaviour through a data pattern such as CQRS; no such decoupling is modelled yet. A call-weighted mean was considered and not chosen.

### 5. Cost is one of four weighted score dimensions, and is engine- and query-aware

Cost was already one of the four weighted dimensions of a query's score (pattern match, complexity, performance, cost), at a 40/30/20/10 default split, with some engines weighting cost differently. That weighting was unchanged by this ADR until Amendment 8 below (#1002), which gives cost the same weight on every engine. What changes is how the cost dimension's value is computed: it is to be engine- and query-aware, factoring in the engine's standing cost shared across the queries it could serve (not the ones it would serve: that count depends on the assignment the score decides, so it would be circular), so that a low-traffic engine with high standing cost scores low on cost for a query it barely serves. The pricing shown in deliverable reports is a separate, unchanged presentation and is not derived from this scoring dimension.

How the code applies it (#494). A classified query's cost dimension on an engine is that query's own estimated monthly cost there (`src/agents/referee/query_cost.py`, read through `ScoringContext.cost_score` by the shared scorer), from the engine file's `[pricing]` inputs (`src/catalog/engines/<engine>.toml`, #923); its tables' cost band (`scoring._cost` and each analysis's size adjustments, which look at no engine's prices and sum a table's traffic over every query on it) no longer reaches it, and stays only in the per-table summaries the deliverables show. The cost has two parts. The standing share is the engine's `base_monthly` divided equally over the queries of the workload the engine could serve: those past its hard exclusion and capability gates (Decision 2 step 2) and, for an engine that is not a system of record, not a write or a locking read (step 3's rule; a cache serves the reads it fronts). A model's flag does not change that count (Decision 11). The variable cost is the query's own call rate times the units each call is billed for at the engine's per-request prices (`read_unit_price_per_million` and `read_unit_bytes`, `write_unit_*`): a call's bytes are its rows (returned for a read, affected for a write, at least one) times the width of a row of its tables (`size_mb` over `row_count`, summed over the query's tables), rounded up to whole units, at least one unit; an engine that bills a read only on a buffer-cache miss (`reads_billed_on_cache_miss_only`, DocumentDB) pays for the share the source's own cache did not serve. An engine billed by capacity (Aurora I/O-Optimized, OpenSearch, ElastiCache) has no per-request price and so no variable cost: its standing cost pays for the capacity, and scaling that capacity with load is not modelled. The monthly total maps to a score with the engine's own per-query cut-off (`max_burden_per_unique_query`, $100): `100 * cut_off / (cut_off + monthly)`, so a query costing nothing scores 100, one costing the cut-off 50, and a $300 standing cost carried by one query 25. Another query reaches this cost only through how many queries the engine could serve, a count its shape can change (a write does not count for an engine that is not a system of record, and a gated query does not count at all); its call rate and size never reach it. Because the count is of queries the engine could serve, the share is small on any large workload (discourse: OpenSearch's $150 over 1,159 queries, DocumentDB's $200 over 1,432), so there whether an engine is worth running for few queries is answered by the reality check's Phase 1, below. A statement with no access-pattern class (`utility`, `unparsed`) keeps the pre-switch rule, its tables' confidence, cost band included (Decision 14 Amendment 5).

Reality check Phase 1's burden is engine-aware the same way (`reality_check_settle._evaluate_engine_removal`): an engine's burden is its standing cost, plus the extra-engine burden, plus the net variable cost of its own native queries, what each costs on the engine less what it would cost on the engine it would move to (its best-scoring eligible alternative, the cheapest of them when several tie). It is below 0 when keeping the engine saves more than it costs, so that engine ranks last for removal. The per-unique-query cut-off and Decision 13's thresholds are unchanged.

**Amendment 8 (2026-10-17, Decision 5, maintainer decision, #1002): every engine weights cost the same, 10%.** Since #494 the cost dimension is the query's own cost on the engine, so the engine is already in the number; a per-engine cost weight then weighs no extra signal and only adds a flat bonus: with every engine's cost score near 100, as on the bundled samples, 15% for DocumentDB and DynamoDB against 10% for Aurora gave the first two about 5 points over Aurora on every query. The common weight is the default's 10%, which Aurora PostgreSQL, Aurora MySQL, both OpenSearch profiles (search 45/25/20/10, time series 40/20/30/10) and every engine with no weights of its own (ElastiCache) already used, so those weights are unchanged. DynamoDB and DocumentDB keep the relative balance of their other three dimensions: each is scaled by 90/85 to fill the 90 points cost leaves, then rounded to whole percent, so DynamoDB's 60/20/5 becomes 63.5/21.2/5.3, written 64/21/5/10, and DocumentDB's 45/25/15 becomes 47.6/26.5/15.9, written 48/26/16/10. The weights are catalog data (Decision 8): each engine file's `[score_weights.<profile>]` tables (`src/catalog/engines/<engine>.toml`; the first profile is the engine's default), with the default split for an engine without them in the catalog loader (`src.shared.catalog.DEFAULT_SCORE_WEIGHTS`). The loader rejects a profile whose four weights do not sum to 1, and a catalog in which any profile's cost weight differs from another's or from the default's. The analysis modules' weight constants and `scoring.DEFAULT_WEIGHTS` are the catalog's view, so a table's confidence in `analysis.json` and in the per-table summaries the deliverables show moves with the new weights too.

### 6. Heterogeneous sources pick exactly one Aurora engine, deterministically

For a heterogeneous source (SQL Server, Oracle, DB2), exactly one of Aurora PostgreSQL or Aurora MySQL is the relational candidate for every query from that source. The choice is made deterministically, with the reasons traced, and feature support for a given query is checked against that chosen engine rather than assumed.

**Amendment 1 (2026-10-14, maintainer decision, #656): Aurora PostgreSQL wins only as the final exact-tie break.** The maintainer decision covers two points and only these: (a) for a heterogeneous source, neither Aurora engine is source-compatible by default (next paragraph); (b) Aurora PostgreSQL wins only when every existing check still leaves an exact tie on total adjusted score, traced as "tie between Aurora MySQL and Aurora PostgreSQL; PostgreSQL preferred on a tie by maintainer rule, ADR-031 Decision 6" (`aurora_choice.EXACT_TIE_RULE_REASON`). That is expected to be rare.

The existing checks that run before (b) predate this decision, and the decision does not change them. First, each engine's per-query scores are summed into a total. Per-operation support is already counted there, because the scorer's hard capability gate scores an engine 0 on a query it cannot serve. Next, the higher total wins outright when the totals differ by more than 5% of the larger one (`aurora_choice.MARGIN_RATIO`). Within that margin, or on an exact tie, a reported workload feature decides: sequences, MERGE, JSON or multiple schemas. With no workload feature, Babelfish compatibility decides for a SQL Server source. With neither, the higher total wins. Every one of these features currently favours Aurora PostgreSQL. Recursive CTEs are not one of them: this decision used to list them, but MySQL 8.0, which Aurora MySQL version 3 is compatible with, has `WITH RECURSIVE` too (corrected 2026-10-16, #920, catalog PR C). Because every SQL Server source reports Babelfish, these checks send every SQL Server close call to Aurora PostgreSQL on dialect alone. The maintainer confirmed on 2026-10-14 that this is intended: Babelfish compatibility stays the tie-breaker within the margin for a SQL Server source (recorded on #445). The one-sided workload-feature step is still under review in #445 and is not part of this maintainer decision. As implemented today, (b) can only fire for an Oracle or DB2 source.

For six SQL features both Aurora engines run natively, the totals compare the two engines on what they can do, not on which of them has a catalog row: each is a fit on both engines' analyses, each with its own sourced score (window functions, recursive CTEs and `LATERAL`, which MySQL 8.0 has; stored routines, a multi-table `UPDATE`/`DELETE` such as PostgreSQL's `UPDATE ... FROM`, and a string aggregate such as `string_agg`, which PostgreSQL has), detected from engine-neutral facts in the source's own dialect (a SQL Server `EXEC` of a procedure, `UPDATE ... FROM` and `STRING_AGG` included), and the table bonus for each is the same on both engines (the fit entries' `table_bonus` and `complexity_feature` in the pattern files since #921, checked by `tests/unit/shared/test_routing_catalog.py`). Full text and upserts, which each dialect writes as its own pattern file, are aligned too (#984): neither counts toward a table's complexity on either engine (a table-level credit would reach every query on the table, against Decision 14), each pattern rates its own statement per query as a `[[features]]` entry (`full_text`, `upsert`) at its documented fit, and the table bonus that feeds only the table-level summary is the same on both engines (checked pair by pair by `tests/unit/shared/test_routing_catalog.py`). Where one engine's documentation states more, its fit score is higher, and that difference is kept: PostgreSQL's `SEARCH` and `CYCLE` clauses and its frame options (recursive CTEs 95 against 90, window functions 90 against 85, `LATERAL` before a function call 85 against 80), MySQL's multiple-table `UPDATE` that changes several tables in one statement (80 against 75). In the per-query class model the aggregation class credits a window function only to a query that has one (`only_when`, Amendment 5 of Decision 14).

The chosen engine is not source-compatible. For a heterogeneous source, neither Aurora engine counts as source-compatible in Decision 2's tie rule or Decision 13's survival rule, whichever one this decision picks. Whether it can serve a given query depends on that query's own operations, not on the choice.

### 7. The reality check is the CTO consolidation review, routed by the same per-query scores

The first assignment can spread a workload across several engines because each fits some queries best. The reality check is the second-level review that asks, per engine already assigned: is this engine worth running for the queries it would serve, given its standing cost, its operational weight, and whether another engine already in the architecture serves those queries well enough? It may remove an engine or move its queries onto an engine already in the architecture. A moved query goes to its highest-scoring engine among the engines that remain, using the same per-query scores the first assignment used — the reality check does not keep a second, independent fit model. It reports every removed engine and every moved query with before and after scores, and claims a saving only for an engine the first assignment actually justified and the source runs today: the source engine itself, or one the collection records in `metadata.engines_in_use`. A candidate engine the plan analysed and dropped costs the customer nothing today, so removing it is never a saving; `report.json` lists it in `considered_not_recommended` with no dollar figure, and `tco_analysis.retired_engine_savings` holds only the engines the source runs (#949).

This supersedes the reality check's own independent capability and scoring logic (ADR-018) and the Aurora-specific absorption pass with its own fitness gate (ADR-021), replacing both with one scoring path shared with the first assignment. The reality check's role as engine consolidation and the human approval gate it feeds (ADR-018, ADR-026) are unchanged by this ADR.

When the mandatory-engine justification floor moves a query off an engine that failed it, a candidate already mandatory for a different engine (data already flowing to it via a signal override, such as a text-search sync) ranks ahead of an equally-scored, non-mandatory candidate (`reality_check_floors._find_best_absorber_for_query`'s `is_mandatory_secondary` bonus) -- a real operational reason (the data is already synced there) rather than a preference of convenience. It applies only after the score itself ties; an exact tie that survives it too still goes through Decision 2's tie-break, never decided by this bonus a second way.

An engine that holds a customer-pinned query is kept (#860). The reality check never moves a pinned query, so the engine stays in the plan and its standing cost is paid whatever the check decides; this Decision's cost question (is the engine worth running for the queries it would serve) is already answered by the customer. So Phase 1 never removes it, the sanity sweep keeps it (#844), and the floors that ask whether the workload pays for an engine (the cost-share floor and OpenSearch's traffic and result-size floor) do not run for it. The per-query search-depth check is not about cost and still applies: a query with no relevance ranking, fuzzy matching or facet leaves a pinned OpenSearch and never joins it, since a read model adds sync scope and eventual consistency per query that such a query gains nothing from. Otherwise a pinned engine is a kept engine like any other: a query leaves it only for a kept engine that scores it higher, and a query that scores higher on it goes there.

### 8. Rules are a pattern-first, engine-neutral catalog in one place

Routing rules move out of per-engine code and into a declarative catalog read by every step: analysis, gates, penalties, scoring, cost, reality-check floors, reports and the UI.

- **One file per access-pattern type** (for example key-value lookup, full text search, transactions), each naming the pattern, the detector that identifies it, and one entry per engine with whether the engine supports the pattern, its score, and a short reason that feeds the decision trace. Each entry also has a `kind` (the engine's analysis reports the pattern as a fit or an anti-pattern; or, for an engine that does not report it, the engine has the needed capability natively, has a bounded redesign, lacks it and runs the pattern only as a scan (`scan`: it loses the pattern's penalty only on a query that crosses the pattern's `scan_threshold`, whose values and sourced reason are in the same file), takes the cross-engine penalty, or is unaffected), because support, score and reason alone cannot say which penalty or exemption applies. For a pattern backed by the hard capability gate, `supported` matches the gate engine by engine: the gate names its pattern capability (`pattern_capability` in `src/catalog/gates.toml`) and the loader rejects a disagreement (#921). A fit entry may also carry the points the engine's table-level score adds for a table showing the pattern (`table_bonus`, `complexity_bonus`, a `bonus_group` counted once, and `complexity_feature` for the engine file's `complexity_by_feature_count`).
- **One file per engine** for properties that do not depend on the pattern: cost and pricing inputs, score dimension weights, justification floors and other thresholds of its own (`[thresholds.<name>]`, each with its reason), whether the engine can own writes, the source engines whose own dialect it is, whether it scores only a query's own matched pattern, what the reality check lets it absorb, and its display name and color. Each engine file has a `status`: `active` (a routing target), `future` (a placeholder, Decision 9) or `legacy` (an id only older reports carry, such as the generic `aurora`; kept so those reports still render, never a routing target).
- **Shared routing data** in three more files (#921): `src/catalog/routing.toml` for the thresholds every engine shares (the target engine count, the differentiation margin, the mandatory-engine cost floor, the Decision 13 saving thresholds, the sanity sweep's orphan count, the Decision 6 margin), each with its reason; `src/catalog/gates.toml` for the hard capability gate (which engines have each capability, the query facts and triage signals that require it) and the per-engine exclusions; `src/catalog/triage_signals.toml` for the engines each triage signal names and the signal overrides. Detection stays in code. What is left in routing code is engine-specific branches, behaviour rather than data, pinned by `tests/unit/shared/test_rule_catalog_complete.py` until #1081 replaces them.
- **Detection stays in code and is engine-neutral.** A detector runs once per query and reports facts (for example a transaction's entity count, or a wildcard's position), not scores. The catalog turns those facts into each engine's support and score, so a given fact is classified the same way regardless of which engine is being scored, and engines differ only in their catalog entries. This removes the previous pattern, where each engine's analysis detected and scored its own patterns independently, which let the same fact be encoded in more than one place with disagreeing answers. Each fact has one definition, in a declared fact module (`src/tools/sql/facade.py` for the parsed facts, `src/tools/sql/regex_facts.py` for their fallback when a statement can't be parsed, `src/tools/sql/query_facts.py` for the text facts and every reader's access to both, `src/shared/unsupported_pattern.py` for the dedup-only `GROUP BY` proof, `src/agents/referee/query_shape.py` for the locking clause, skipped locked rows, the primary-key ordered row limit and the single-table access shape of Decision 14 (only those: its `GROUP BY`, `ORDER BY`, `LIKE`, `SELECT` and range readings come from `regex_facts.py`), `src/agents/referee/utility_statements.py` for utility statements), read in the source engine's dialect, and every reader uses it (#893). The guard is a tripwire, not a proof: it fails a SQL or fact keyword (a regex, an `in` test, a string method or a keyword collection) outside the declared fact modules, a facade fact or text detector that two facts read, and two facts that agree on nearly every query of the samples without a declared reason; a copy that spells its keywords some other way still needs review. A fact that needs the schema reads it through the same modules: a timestamp column is one whose collected data type is a date, datetime or timestamp in the source dialect (`query_facts.is_timestamp_type`), its table resolved from the facade's column references and aliases (`SqlFacts.columns`); the name list (`regex_facts.TIMESTAMP_COLUMN_NAMES`) is read only when the collection has no column types, or for a column whose table can't be told (ambiguous, not collected, or a statement the facade can't parse), and the analyses' decision traces list those columns (maintainer decision, #935).
- **Validation.** The catalog loads into typed models at start-up, so a missing or mistyped field fails loudly. A completeness check requires every pattern file to have an entry for every engine except a `legacy` id (a future placeholder's entry is its written "not modeled yet", Decision 9), so adding an engine or a pattern fails with the exact list of missing decisions instead of silently defaulting to "unsupported."
- **Comparison.** A rendered pattern-by-engine matrix, with support, score and reason, plus the engine properties side by side, is the one place that answers "why does this engine's score differ from that one's for this pattern?" Display names and colors used elsewhere are generated from the engine files rather than kept as separate copies.
- **Adding an engine** means one engine file, one entry per pattern file (the completeness check lists exactly which), and the engine's own detection code where a pattern has no existing detector. No change to the resolver, the reality check, the reports or the UI.

**Amendment 6 (2026-10-16, #920; the maintainer decided on 2026-10-16 to fix catalog accuracy before the #728 switch, and this rule is the engineering proposal for its penalty part, open for maintainer review on its PR): one rule sizes every penalty, and a fit pattern tests the access pattern its reason describes.** Before it, every DocumentDB anti-pattern and DynamoDB's full-scan anti-patterns cost 0 points while Aurora's cost 15 to 35, so the same kind of finding moved queries on one engine and only added a sentence on another: an engine bias held in data. Each pattern file that carries a penalty, or has an `anti_pattern`, `penalized`, `scan` or `redesign` entry, now names a `penalty_basis`: the consequence the engines' public documentation states for a query showing the pattern. The basis fixes the points, the same for every engine (`src/shared/catalog/patterns.py`, `PENALTY_POINTS`), and the loader rejects a penalty that is not its basis's points:

| Basis | Points | The engine's documentation says |
|---|---|---|
| `cannot_run` | 40 | it cannot run the pattern at all (a `penalized` entry; an anti-pattern whose entry is `supported = false`) |
| `needs_redesign` | 30 | no server-side operation serves the access path: it needs precomputation, a data-model redesign or another engine |
| `reads_more_than_returns` | 20 | it runs the query, but reads more than it returns (a scan, a per-collection join stage), so the work grows with the data, not the result |
| `workload_fit` | 20 | it runs the query natively, but the query uses none of what distinguishes the engine, and another candidate's documentation names this access path as its own (the Aurora anti-patterns, including Decision 14's whole-workload ones) |
| `bounded_limit` | 10 | it runs the query within a documented bound the design must respect: a page size, an item count, a document size, a version or a cluster type |
| `guidance_only` | 0 | no limit the query hits, or another pattern already prices the same fact (a leading-wildcard scan is `substring-match`'s, Decision 2 step 5); the entry is guidance |

Every `anti_pattern` entry's reason cites the public documentation it rests on, and a file may say why its consequence is that basis in `penalty_why`, rendered next to the penalty in the rule catalog: DynamoDB's `wide-transaction` is `bounded_limit` (10) because a write wider than one transaction runs as bounded calls of at most 100 items, never needing a data-model redesign (#916). The penalty is then the same mechanism for every engine: the biggest penalty a query shows on an engine applies there (`query_scoring.build_anti_pattern_map`), and the scorer names no engine. For the same reason, a fit pattern's detector tests the access pattern its reason describes, read from the SQL facts and the collected schema, never a column count, nullability or call rate alone: DocumentDB's `product-catalog`, `polymorphic-data` and `content-management` need a key-anchored read of an entity with variable attributes (`src/tools/analysis/variant_attributes.py`; one `variant-attributes` pattern since #967, scored 80), DynamoDB's `write-heavy-ingestion` needs a write by key, and DynamoDB's `low-frequency-read` and `low-frequency-write` are no longer fits. DynamoDB's key patterns read their key from the same facts (`src/tools/analysis/key_access.py`), not the collector's `filter_columns`: `key-value-lookup` needs a read by a full primary or unique key, `range-query` a partition-key equality plus a range on another column of the same table, `metadata-config-store` a keyed read of a small, read-mostly table, the parent-child, co-access and junction patterns a key-anchored join, `time-series-event-log` an append-only table or an entity-anchored time range, and `session-store` a keyed session statement; the first rows of a whole table in some order with no key value are DynamoDB's `ordered-scan` anti-pattern, since a Scan returns no order. A key lookup is Aurora's native access path too, so Aurora's own `key-value-lookup` fit (a B-tree point read, 80) replaces the 60 its class score borrowed from `standard-crud`. How often a query runs is not an access pattern; that on-demand capacity suits sporadic traffic is cost evidence, for the cost dimension (Decision 5, #494). An overlay engine that owns no query (ElastiCache) may still read the call rate, since a cache's value is its hit rate. DocumentDB's remaining fits test their access pattern too (#967): the JSON fit is one `json-document-query` pattern for every engine (merged from `flexible-schema`, `jsonb-operations` and `json-document-query`), and it needs a query that reads JSON paths (the `json_access` fact), not a JSON column on the table; `aggregation-pipeline` needs a grouped aggregate or one over rows no key anchors, not one key's `COUNT`; `write-time-aggregation` is a design every engine can use, so no engine's analysis reports it as a fit; and the DocumentDB trace's `polymorphic_tables` lists the tables the variant-attribute facts name. A saved analysis may still carry the merged ids; no reader looks a fit's type up in the catalog, so it loads unchanged.

The detectors price the shape the documentation describes (#968). DynamoDB's `complex-aggregation` (`needs_redesign`) is a `GROUP BY`, or an aggregate over rows no key anchors or over a join; an aggregate over one key's rows of one table (`COUNT(*) WHERE post_id = ?`) is a Query on that key with `Select = COUNT` and is not the pattern (the hard `aggregation` gate still rules DynamoDB out of every aggregate, Decision 2 step 2). The window functions split by what DocumentDB's documentation says: `$setWindowFields` runs ranking functions and running aggregates on DocumentDB 8.0.2 or later on an instance-based cluster, so a ranking window function is the `ranking_window` gate capability DocumentDB has, priced by the `window-functions` anti-pattern (`bounded_limit`), while `LAG` and `LEAD` (`$shift`) and `NTILE` (no bucketing window operator) run on no version: the `offset_window` gate capability, which DocumentDB lacks. `scan_engine` keeps the recursive CTE. DocumentDB's `faceted-analytics` is several groupings of one row set (`GROUPING SETS`, `ROLLUP`, `CUBE`, the facade's `grouping_sets` fact), which `$facet` serves on 8.0.2 or later (`bounded_limit`); a `GROUP BY` over several columns is one `$group` with a compound `_id` and is not the pattern. The basis points were tested against the benchmark answer keys (`benchmarks/cases/assignment`, #968): setting each basis's points to 0, 10, 20, 30 and 40 in turn leaves both reviewed cases at 100% acceptable accuracy, because the answer-key queries show only three anti-patterns (`complex-aggregation`, `multi-index-joins`, `high-frequency-pk-lookup`) and none of them decides an answer. The answer keys therefore do not constrain the points yet; they stay the documented consequence's starting values until reviewed cases whose answers turn on an anti-pattern exist (#1084).

### 9. Neptune and Keyspaces are future placeholders

Neptune and Keyspaces are added to the catalog as placeholders only, each marked as a future enhancement with an explicit "not modeled yet" entry in every pattern file so the completeness check passes on a recorded decision rather than a default. A placeholder engine is never a routing candidate and routing output is unchanged by its presence. Modeling either engine for real — giving it real scores, detection and schema-design support — is separate, later work.

### 10. Every routing change reports its per-query effect

A routing change reports, before and after against the prior behavior, the per-query effect on every available sample workload, for both the first assignment and the final (post-reality-check) assignment. Engine totals alone are not sufficient evidence. If a score-based result looks wrong, it is reported as a finding, not silently corrected with a bias toward a preferred engine.

**Amendment 3 (2026-10-14, planned design decision from the #489 routing plan, #616): every engine change is a ledger entry.** A query's engine (`assigned_engine`) and its unresolved tie (`tied_engines`) change in one place only: `move_ledger.apply` / `apply_to_assignment` (`src/agents/referee/move_ledger.py`), which records a Move (`src/contracts/move_ledger.py`) naming the pass, the rule, the engine the query left and the one it lands on, the shared scorer's scores on both, the runner-up, the evidence the pass saw and who caused it (a rule, the customer or a model's flag). The ledger also holds each query's current tie (`MoveLedger.tied`), and the first assignment builds v1's ties from it. Each assignment version carries exactly the Moves that produced it (`Assignment.moves`, per version), and replaying the version it was derived from (nothing, for v1) plus those Moves rebuilds its engines and ties; every writer of a version (the first assignment, the reality check, the customer gate, the post-schema router's reroute and rollback) checks that with `move_ledger.check_replay` before writing and refuses a version that does not replay. The cache owner normalisation of an assignment written before the cache overlay is a Move too (`cache_owner_normalize`), wherever it runs. This is how this decision's per-query report reads one record instead of several that can disagree. No module other than `move_ledger.py` may write `assigned_engine` or `tied_engines`, and the guard has no exceptions. The post-schema router's reroute version records one `post_schema_flag` Move per moved query (rule `flag.capability_gap`, actor `model_flag`, #489 Track L PR4); when the redesign on it fails, the rollback version that restates the earlier routing records the reverse Moves, one per Move of the reroute, undone in reverse order back to the engine and tie the query had (rule `rollback.redesign_failed`, actor `rule`, #770); its replay check compares the result with the restated version, so a query that differs without having been rerouted is refused. One replay rule covers every version. The reality check's own records are derived from its Moves rather than kept beside them (#616): each consolidation record is a net move the Moves replay to, a sanity-sweep `removed` verdict and its records come from the sweep's Moves, and a `moved` flag verdict takes its destination and scores from its Moves. What a Move does not carry stays computed where it is decided: the pass's reason text, the retained queries of a partial consolidation (a query that did not move has no Move), the removed engine's analysed cost (the saving, counted once per engine) and its first-assignment `workload_justified` verdict, and the `kept` sweep and `kept`/`ignored` flag verdicts, which move nothing. This records the design decision of the #489 routing plan (Track L); it is not a separate maintainer decision.

### 11. Models explain; they do not decide

Assignment and reality-check routing remain deterministic. A model may explain an assignment in natural language; it never decides or changes one. Running without a model gives the same assignment and reality-check result as running with one.

**Amendment 2 (maintainer decision, 2026-10-14, #647, #629): a model's flag is evidence; the scorer decides.** A model may flag queries it judges an engine unable to serve, in one structured shape for both LLM modes (`src/contracts/model_flag.py`: the query ids, the engine they are on, a reason category and a short explanation). A flag never names a destination. An accepted flag marks the flagged engine unable to serve those queries, a capability gap for those queries only (`ScoringContext.flag_gaps`), and the shared scorer re-routes them to the best engine that may own them, with exact ties through `tie_break.break_tie` and co-dependency groups moved as one unit (`src/agents/referee/model_flags.py`). The before and after scores are recorded with the flag. A reality-check flag re-routes its queries only among the engines the reality check kept: it never brings back an engine the check removed and never re-settles any other query. When no kept engine can take them, the queries stay where they are and the record says why. The same holds after schema design (#629): the reality check consolidates first, and schema design and PE review work on the assigned queries. A PE reviewer's routing flag (or a designer's unsupported pattern) counts only for a query on the reviewer's own engine, and the post-schema router re-routes it, with its co-dependency group, only among the engines the approved assignment keeps. A reroute writes a new assignment version (`source = post_schema_routing`, status `rerouted_after_approval`, never the customer's approval it edits), and schema design runs again on that version for every engine the moves touch (the one a query left and the one it joined), so the design and the assignment agree. Every deliverable lists the queries moved after approval, why, and how to override them; the run does not pause for a new approval. Both LLM modes run this review and router (#1059): Bedrock mode inside schema design, a headless Claude Code run as external steps (`scripts/run_pe_review.py`, `scripts/run_post_schema_routing.py`) over the same answer contract, router and move ledger, so the same flags give the same assignment version. That parity is routing only: the review's revision round (a design revised on the review's change requests, and `pe_notes` turned into trade-offs) is Bedrock-only until #1070, so headless designs and deliverables can still differ from Bedrock's while their assignments match. A model therefore still never decides an assignment: a run with flags differs from a run without a model only where a flag removed an engine from a query's candidates, and a run with no flags gives the same result as a run with no model.

### 12. A still-unresolved tie gets a placeholder, decided by settled workload share then a stable hash (maintainer decision, 2026-10-12)

Decision 2 leaves some ties with no rule at all: no tied engine is source-compatible, and (in the reality check) no tied engine is the query's current one either, or two different tied engines are each current for different members of the same co-dependency group. The query still needs an engine to sit under until the customer picks one, so a placeholder is used -- but the placeholder is not itself a new ADR-031 preference, and the structured, customer-visible fact is the tie itself (`QueryAssignment.tied_engines`), never silently hidden behind the placeholder's pick.

The placeholder, in order: first, whichever tied engine already carries more of the SETTLED workload for this run -- the number of queries this run decided without a tie (never another placeholder pick, so one tie's placeholder can never feed another tie's count, which would make the result depend on evaluation order); second, when that count is also tied (including the common case where neither engine has any settled workload yet), a stable hash of the query id and the candidate engine name. Favoring the engine with more settled workload is consolidation-consistent with Decision 7's CTO review, which already prefers fewer, larger engines over more, smaller ones -- it is not a preference for one engine's name or brand. The hash fallback exists only so the result is deterministic across runs on the same input; it is a hash OF the engine's name together with the query id, not a comparison BY the name -- an engine's name, traffic or query count is never read to decide which one wins by being who it is, only hashed alongside the query id to pick a stable, unpredictable split when the settled-workload count cannot.

A tied query is evidence for exactly the ONE engine the placeholder picks -- never for every tied engine, and never for none. Phase 1 counts it as that one engine's native workload when deciding whether the engine earns its place; excluding it from every engine's evidence could leave an engine whose only queries were tied uncommitted with no fallback (crashing the placement invariant when nothing else was eligible either) or let a tied workload silently fall to a far weaker committed engine because Phase 1 never got to evaluate either tied engine at all. The query still carries `tied_engines` and stays visible to the customer either way. If the picked engine is later removed anyway, Phase 2 re-resolves the tie among whichever of the originally tied engines are still committed, never opening the choice to the wider committed set while at least one of them survives; only once none of the tied engines survive does the query fall back to its best-scoring surviving engine among the rest, with an honest reason, and `tied_engines` clears -- the tie is genuinely gone, not re-placeholdered.

Eligibility gates that key off "the query's current engine" (the specialist-absorb exemption, the join-consolidation block) treat every one of a tied query's `tied_engines` as current, not just the one placeholder happens to be recorded as -- otherwise an arbitrary placeholder pick could silently decide a gate's answer instead of just sitting the query somewhere pending the customer's choice. The same stable key (sorted member ids for a co-dependency group, never input order) feeds the placeholder's hash fallback everywhere it is used -- the first assignment, the reality check's placement step, and its mandatory-engine-floor absorber -- so the same tie cannot re-pick a different engine purely because of evaluation order.

A co-dependency group has one tie (Decision 4): the engines every member that carries a tie is tied on, in `tie_break.group_tie` (#833). A member with no tie adds no constraint, an intersection of fewer than two engines is no tie (the group's scores decide), and the answer never depends on member order; members whose ties differ are logged as a warning, since the first assignment gives every member the same tie. The reality check's placement and sanity sweep, a model's flag and the post-schema reroute all take a group's tie from it, so a group with one tied member is re-resolved among that member's surviving tied engines first, whichever member comes first. A surviving tied engine counts only if it can take the whole unit (kept, eligible and serviceable for every member, `tie_break.tied_survivors_first`); when none can, every engine that can take it competes. This records the design decision of #833; it is not a separate maintainer decision.

This is implemented once, in `tie_break.pick_unresolved_tie_placeholder`, so the resolver, the reality check's placement step, its mandatory-engine-floor absorber and its eligibility gates cannot drift from each other on it; the settled-workload snapshot itself is computed once, by the resolver, and persisted for the reality check to reuse (`RoutingTrace.settled_counts`) rather than each stage measuring "settled" differently. A future ADR-031 amendment may replace this placeholder; until then, this is the one rule governing it.

**Amendment 10 (2026-10-17, maintainer decision, #1003): a still-unresolved tie is one customer choice per table, and `--auto` decides it.** The placeholder above stays where the query sits until a choice is made; this amendment says how the choice is presented and who makes it. The open ties are grouped per table (`pending_choices.build_pending_choices`): a tied query goes under the table it writes (its write group, Amendment 9), else the one of its tables the most tied queries touch, then by name; queries that must place as one unit (co-dependency and write groups) are always in the same choice, which then ties between the engines all its queries tie on (or, when they share fewer than two, every engine any of them ties on); other queries tied on different engines never share one. The customer gate, the UI, the ATX review tool, `/modernize` and every deliverable present one choice per table with its queries listed under it and the deciding facts: each tied engine's score (the whole-point score routing compared) and its unrounded score (the shared scorer's same score before it drops its fractions, `score_query_for_engine(..., exact=True)`; never a routing input), why they tie, and each engine's trade-off (whether the plan already runs it, the gap before rounding, and, for a write, that it becomes the table's source of truth). A pick applies to every query of the table through the customer gate (`customer.pick` Moves). Interactive runs never break such a tie on their own: without `--auto`, `/modernize` asks one question per table, and a model never picks. `--auto` means "decide for me" and leaves no choice pending: per table, `tie_break.decide_for_me` picks, in order, the higher unrounded score (the mean over the table's queries, a write group's call-weighted mean, Decision 4 Amendment 4); then the engine the plan already uses more (`tie_break.settled_counts`, never a tied query, so the answer does not depend on the order choices are decided in), which keeps the plan to fewer engines; then `break_tie` (source-compatible, then stability: the engine the queries already sit on, then the placeholder's hash on the table). Each pick is a ledger Move (pass `auto_pick`, rule `tie.decided_for_you`, actor `rule`) with the alternative as runner-up and both engines' whole-point and unrounded scores in its evidence, and the version records the choice (`Assignment.auto_decided_choices`) while all its queries stay on that engine; the deliverables mark it "decided automatically, review if needed", and a customer pick on one of its queries, in the UI or anywhere else, replaces it. The issue's review warned that unrounded totals move in 5-point input steps; the maintainer chose them as the first input anyway, because they are the scorer's own figures and only order engines that tie at the resolution routing compares. A version whose only change is those decisions is written with `status` and `source` `auto_decided`, never as a customer edit; a batch that also carries a customer pick is a customer edit (`customer_modified`, `customer_gate`), its `--auto` Moves still the rule's. The deterministic pipeline does not pass through the gate, so this amendment changes no engine there: which ties are open on each sample is in the routing snapshot (`tests/e2e/baselines/routing_snapshot.json`, Decision 10), and `tests/e2e/test_pending_engine_choices.py` checks that `--auto` decides every bundled sample's open ties by this rule.

### 13. The source-compatible engine is not removed on cost for an engine that serves its queries no better, unless that engine is much cheaper (maintainer decision, 2026-10-13)

Decision 2's tie rule also governs which engine the reality check removes, not only where a query goes, and it extends to a margin too small to count as unique value: nobody chooses a NoSQL engine over the source-compatible SQL engine for a small saving. When the source-compatible Aurora engine scores every one of its queries equal to or higher than its best other committed engine, the reality check keeps it instead of removing it on standing cost. Before this decision, Phase 1 removed the engine with the highest burden per unique query, so Aurora's $250 standing cost against DocumentDB's $200 removed Aurora from a workload it served at least as well, on a $50 difference (#600).

The one exception: the alternative is at least 40% cheaper in standing cost AND saves at least $100 a month. Both conditions must hold, and each is inclusive at its boundary. Aurora at $250 against DocumentDB at $200 is 20% and $50, so Aurora stays; against DynamoDB at $0 it is 100% and $250, so the cheaper engine wins. The alternative for a query is its best-scoring other committed engine (every one of them, when several score the same); the exception must hold for every one of the source-compatible engine's queries through at least one of its best alternatives.

The rule applies only when the source-compatible engine scores at least as well on every one of its queries. If any query scores lower on it than on another committed engine, the existing rules (unique value, then the burden rank) decide as before. Apart from the cost dimension inside every engine's score (Decision 5), which shares each engine's standing cost over the queries it could serve, this is the only place standing cost is weighed against the source-compatible engine's score; it is implemented once, next to the shared tie-break, in `tie_break.source_compatible_engine_survives`, with both thresholds as named constants (`tie_break.CHEAPER_ENGINE_MIN_SAVING_SHARE`, `tie_break.CHEAPER_ENGINE_MIN_SAVING_MONTHLY`).

A heterogeneous source (SQL Server, Oracle, DB2) has no source-compatible engine, so this rule does not apply to it; the one relational engine Decision 6 chooses for it gets no protection from standing cost under this decision. This was confirmed on 2026-10-14 (#656, see the Decision 6 amendment).

### 14. A whole-workload anti-pattern's table-level rule only complements the per-query check (maintainer decision, 2026-10-14, #692)

Some catalog anti-patterns are defined over a table's whole workload. Today those are `aurora-anti-05` ("no-relational-need": no foreign keys, no join participation, every application query single-table CRUD) and `aurora-anti-06` ("single-access-pattern-table": at most 2 application queries, all single-table, all by primary key or a single column filter, no foreign keys; #714). For `aurora-anti-06`, "by primary key or a single column filter" means the shared per-query CRUD check below (`query_shape.single_table_access_shape`), not a separate count of filter columns. Such an anti-pattern runs in two steps, always in this order:

1. **The per-query check, first.** Each application query on the table is classified on its own access pattern (`query_shape.single_table_access_shape`):
   - **CRUD**: a point or simple-key read or write. `ORDER BY <the table's own primary key>` with a literal single-row limit is a key-value lookup and counts, in every spelling: `LIMIT 1`, `TOP 1` / `TOP (1)`, `FETCH FIRST|NEXT [1] ROW(S) ONLY` (no count means 1), MySQL `LIMIT 0, 1`, and an explicit `OFFSET 0` (`LIMIT 1 OFFSET 0`, the T-SQL `OFFSET 0 ROWS FETCH NEXT 1 ROWS ONLY`). The same holds at any offset, literal or placeholder: `LIMIT 1 OFFSET 5`, `LIMIT 1 OFFSET $1`, `OFFSET m LIMIT 1`, MySQL `LIMIT 5, 1` / `LIMIT ?, 1`, and `OFFSET n ROWS FETCH NEXT 1 ROW ONLY` with `n` a literal or a placeholder.
   - **Ordered 1:M read**: the same primary-key-ordered read with any other limit: `LIMIT n` with n > 1, a bind-parameter limit with no evidence it is 1, `TOP n PERCENT` (`TOP (1) PERCENT` included), or `WITH TIES` (which can return more than n rows), with or without an offset (`LIMIT 5 OFFSET $1`, `OFFSET 5 ROWS FETCH NEXT 1 ROW WITH TIES`). A key-value store models it, so it is neutral: neither CRUD evidence nor relational evidence. It is never labelled a key-value lookup. A neutral read gives no relational need, so a per-table rule such as `aurora-anti-05` or `aurora-anti-06` may still apply to it (step 2). (These lists spell out the 2026-10-14 maintainer rule, "a literal single-row limit is key-value; a placeholder or any other number is neutral", for every row-limit form; #782. Clarification, maintainer decision of 2026-10-15 posted on #782 (#857): a single row from a known table at any offset is a key-value lookup, not a neutral read. It supersedes the 2026-10-14 reading that any skip, even with a limit of 1, makes the read neutral. A read that skips locked rows is still at most neutral, see below.)
   - **Relational**: anything else. A relational query never takes the penalty.
   - **A locking clause does not change the shape** (#799; Decision 3: DynamoDB supports transactions, so the score reflects shape). `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` (with `OF` or `NOWAIT`), MySQL `LOCK IN SHARE MODE` and a SQL Server `WITH (UPDLOCK | HOLDLOCK | XLOCK | SERIALIZABLE ...)` hint lock the rows a read returns. They do not change which rows those are, and `NOWAIT` changes only what happens when a row is already locked. A query is classified as the same read without the lock: a locking point read by key, or a locking `ORDER BY <primary key>` read with a literal single-row limit, is CRUD; a locking read in primary-key order with any other limit is an ordered 1:M read; a locking range, aggregate or non-key-ordered read stays relational. The exception is a lock that skips rows: `SKIP LOCKED` and the T-SQL `READPAST` hint return the first row no other transaction holds (a work-queue claim), not the row the key or key order names. That is an unknown row (an offset, by contrast, names a position in a known order, #857), so it is at most an ordered 1:M read and never CRUD, with or without an offset; relational evidence stays relational. The lock is recorded separately as a transactional need (`query_shape.locking_clause`, the `locking_clause` field of each query in the Aurora decision traces, with hint names limited to the fixed SQL Server table-hint list). It adds no penalty or bonus to any engine. Keeping a locking read off an engine that is not a system of record is a separate ownership rule (Decision 2 step 3, `cache_overlay.is_locking_read`); it reads the lock with this same `locking_clause` (#838). A lock word in a comment, a string literal or a quoted identifier (a column named `"update"`) is not a lock. (Engineering decision under Decision 3, open for maintainer review on #799.)
2. **The table-level rule, as a complement.** The anti-pattern's own table condition (for `aurora-anti-05`, no foreign keys and no join participation; for `aurora-anti-06`, at most 2 application queries and no foreign keys) can add the penalty only when step 1 found no relational query on the table. Ordered 1:M reads are neutral here too: they neither block the rule nor are needed for it, so a table whose application queries are all ordered 1:M reads is treated exactly as it would be without this classification. The penalty then covers the table's CRUD and ordered 1:M queries, because neither has a relational need. It never overrides a per-query result.

Why the table-level rule exists at all: the catalog rule is a negative claim about the table, that it needs nothing relational. One aggregate, window function, subquery, range or unkeyed write, or ordering over non-key columns on the table makes that claim false. Penalising the table's keyed reads and writes while its relational queries stay on the relational engine would split one table's writes across two engines (the `web_crawler_requests` case found in #686's review). The table-level rule never assigns a query and never adds to a score. It only gates that one penalty, and every query is still scored from its own tables (Decision 1). The per-query facts underneath are engine-neutral and defined once (Decision 8).

A new anti-pattern may use a table-level rule only if its catalog text defines it over the table's whole workload, and only in this order: per query first, then table.

**Amendment 5 (2026-10-15, maintainer decision, #728): each query is scored on its own access-pattern class, and a key-anchored join is a key-scoped 1:N read, not a relational need.** A query's pattern score on an engine comes from what the query itself retrieves, never from the strongest pattern on its tables (no inheritance) and never from how its SQL happens to be written. We were too strict in a relational mindset in which a query must move exactly as written: a NoSQL design denormalises an entity and its children, fetched by key, into one item collection, and a key-value lookup performs better on DynamoDB regardless of the engine it runs on today. This supersedes the reading of this decision, and of `aurora-anti-05`'s "no join participation", in which any join is a relational need: a join in which every table is reached by key from a key predicate on one of them is a key-scoped 1:N read. #885's per-table "strongest pattern" rule is not adopted (#885 was closed in favour of this amendment).

Every query gets exactly one class (`src/agents/referee/access_pattern.py`, `classify_query`). Classes, in severity order (when a statement shows several shapes, in one scope or across subqueries, the later class wins):

| Class | Example | Leaning |
|---|---|---|
| Key lookup | `WHERE pk = ?` (any limit), `WHERE id IN (...)`, a full unique-index key, `ORDER BY pk LIMIT 1` at any offset (#857), an `INSERT` | key-value: DynamoDB-friendly |
| Key-scoped 1:N | `WHERE parent_id = ?`; `orders JOIN order_items ON fk WHERE orders.id = ?`; `COUNT(*)` with no `GROUP BY` over either; a residual `LIKE` on keyed rows | item collection: DynamoDB-friendly, not a relational need |
| Small reference-table read (Amendment 7) | every row of a table of at most 10,000 collected rows, with no predicate and no row limit (`SELECT * FROM feature_flags`) | neutral: reference data every engine serves from memory |
| Range or ordered read by key | `WHERE pk BETWEEN ...`, `ORDER BY id LIMIT $1`, a read with no predicate, any read that skips locked rows | neutral: an index range scan, and a Scan on a key-value engine (no partition value) |
| Ad hoc filter | filters on non-key attributes with no anchoring key, an `OR` of predicates, a timestamp range, an unkeyed bulk write | relational, document or search |
| Unanchored join | a join in which some table is not reached by key from a key predicate | relational |
| Aggregation | `GROUP BY` with an aggregate function, an aggregate over rows no key anchors, a windowed aggregate (`SUM(...) OVER`) | relational or analytics |
| Text search | with no key anchoring the rows: `LIKE '%x%'`, regular expressions, similarity, full text | search; Aurora PostgreSQL with pg_trgm |

The row-limit rule is the maintainer's, and it applies to a read with no pinned key value: `ORDER BY <primary key>` with a single-row limit (`LIMIT 1`, also `LIMIT 1 OFFSET n`, in every spelling step 1 above lists) is a key lookup, and `LIMIT n` or a placeholder limit in key order is a range read. A read that pins a full primary or unique key (`WHERE pk = ? LIMIT ?`) returns at most one row whatever its limit, so it is a key lookup; `LIMIT 1` on a non-unique key stays a key-scoped 1:N read. A read that skips locked rows is at most a range read, as in step 1. A statement that reads or writes no table (`SET`, `SHOW`, transaction control, DDL, `SELECT 1`) is labelled `utility`, and a data statement the SQL facade cannot parse is labelled `unparsed`; neither takes a class score, so both keep today's score.

This changes step 1's per-query check for the switch, and the switch replaces these rules in `query_shape.single_table_access_shape` (Amendment 7): a range over a key with no pinned value (step 1: relational) becomes a neutral range read; a read with no predicate, ordered by a key with a row limit or not ordered (step 1: CRUD when unordered, relational when ordered by non-key columns with no limit) becomes a neutral range read, and an `ORDER BY` with no row limit no longer changes the class; an aggregate with no `GROUP BY` over rows one key value addresses, on one table or over a key-anchored join (step 1: relational), becomes a key-scoped 1:N read; a `GROUP BY` that combines no values (step 1: relational, with `DISTINCT`) only de-duplicates the rows it reads, so it takes their class; and a join in which every table is reached by key from a key predicate (step 1: relational, as "join participation" for `aurora-anti-05`) becomes a key-scoped 1:N read.

Each class is detected from the shared SQL facts, never from new regexes: `src.tools.sql.facade.access_facts` reads the sqlglot tree (the tables each scope reads, the columns it pins to a value or bounds by a range, the column pairs that join two of its tables, its order, row limit, grouping and aggregates, and its own text-search predicates), using the facade's definitions shared with `SqlFacts` (#875): `wildcard_leading` is a pattern whose first part is a literal starting with `%`, a `LIKE ?` is its own fact (`like_parameter`, an unknown pattern), and a ranking or offset window function (`ROW_NUMBER`, `LAG`, ...) is not aggregation. The classifier adds the schema's keys. A key column is a primary-key column, a foreign-key column, a unique index's leading column, or the leading column of a non-unique, non-text index unless that column is a date or timestamp (an index on a point in time orders rows, it does not address an entity) or the collector's statistics show at most one distinct value per hundred rows; with no statistics the rule holds and the class's reason says the key is unconfirmed. A unique key is the primary key or the columns of a unique index; a join edge is a column equality with a key column on at least one side. A text-search predicate makes the class text search only in a scope no key anchors; on keyed rows it filters one item collection. A `LIKE ?` shows no text search: its pattern is unknown (#912), so no text search is visible and its scope is classed by its other predicates, usually as an ad hoc filter on its column (#920, catalog PR C; OpenSearch's triage text-search signal still names it).

A query's pattern dimension on an engine is its class's score there: the highest rating that the pattern files listed for the class in `src/catalog/access_classes.toml` give that engine, where a `fit` entry counts at its `score` and a `native` or `unscored` entry at its `class_score` (the engine serves the pattern although its analysis does not report it; every `native` entry of a listed pattern must carry one), or 0 when none of them rates it. A `class_score`'s `why` cites the engine's public documentation for its access path, or, where the catalog has no engine-specific evidence yet, the entry is a parity anchor (#936): it names the read pattern whose rating it borrows (`parity_anchor`; never a `write_pattern`, and the loader rejects one that is), its `why` says "parity anchor: no engine-specific evidence yet" with the borrowed `(<pattern>, <score>)`, and the access-pattern record says so for each query and engine whose class score is one (`parity_anchors`; the shadow decision trace until Amendment 7, `assignment/v<N>/access_patterns.json` since). The anchors left are DocumentDB's key lookup (80, Aurora's own key-lookup rating; it borrowed `standard-crud`'s 60 before) and range read (85) and the DocumentDB and OpenSearch ad hoc filter (75, Aurora's secondary-index read; it used to borrow `multi-row-mutation`, a write pattern, and no class lists a write pattern now). Each is replaced only by documentation plus a measurement (#936). A write (an `INSERT`, `UPDATE`, `DELETE` or `MERGE`) is rated only on a system of record, so no class credits OpenSearch or ElastiCache for one (Decision 2 step 3). An anti-pattern listed for a class records why an engine gets 0 and adds nothing: an unanchored range is `frequent-full-scan` on DynamoDB, not `range-query`, which needs a partition value. A class may make a pattern depend on a query fact (`only_when`): `time-aggregation` (OpenSearch 90) counts in the aggregation class only for a query whose `GROUP BY` truncates or extracts a date or time (the facade's `time_bucket` fact: `date_trunc`, `TRUNC`, `DATE()`, a cast to `date`, `YEAR`/`MONTH`/`DAY`, `EXTRACT`, `date_part`/`DATEPART`, `to_char`/`DATE_FORMAT`, `strftime`, written out or named by alias or position; #920), and `window-function` only for a query with a window function. In the text-search class each text pattern counts only for its own kind of text search (the facade's text-search kinds: a full-text match, a leading-wildcard `LIKE`, a regular expression, a similarity function), so a `LIKE '%x%'` is not rated by a full-text index that does not serve it. Each engine's number there is its own access path: an index serves the match (OpenSearch; Aurora PostgreSQL's `pg_trgm` for `LIKE`, regular expressions and similarity; MySQL `FULLTEXT` and PostgreSQL `tsvector` for a full-text match; DocumentDB `$text` within its documented limits, 60), or the engine reads every row (Aurora MySQL for a leading wildcard or `REGEXP`, DocumentDB for a non-prefix `$regex`). 45 is the named "runs, but reads every row" level: below the narrowest index that serves a text search (DocumentDB `$text`, 60) and above "cannot run" (0), and #982 reuses it for a regular-expression scan. It applies unconditionally, at any table size and call rate: in the class model a rare word search on a small table costs Aurora MySQL and DocumentDB 35 pattern points against `pg_trgm`, unlike `substring-match`'s penalty (Decision 2 step 5, #911), which lands only on a frequent query on a large table. The class score adds no second penalty; the switch PR (#728) lists the leading-wildcard and word-search moves off the source-compatible engine separately so they are reviewed knowing this. No engine outscores OpenSearch on any text search. The range class lists no timestamp-range pattern, because a timestamp column is never a key and the range class never holds a timestamp range; an unanchored timestamp range is an ad hoc filter and is scored there. The numbers stay in the pattern files (Decision 8); the class file only says which patterns describe each class, and the scorer names no engine. The other three dimensions, their weights (Decision 5), the gates and the penalties are unchanged, and each table's complexity and performance still enter through the query's own tables only (cost too until #494 made it the query's own, Decision 5). The weights are the ones each engine's analysis used for the table (`src/tools/analysis/score_weights.py`; the engine files' `[score_weights]` since #1002, Decision 5), never read from the decision trace (ADR-017 Decision 3). There is no all-tables fallback: a query with no rated table of its own scores 0. A pattern-only engine (OpenSearch) scores 0 on a class its catalog does not rate. Consequences the switch must keep: more relational evidence found on a table can never lower an engine's score for a query (#784), and no query's score depends on other queries on the same table (#885).

Rollout was shadow first, then switch (Amendment 7 made the switch and retired the shadow, so this paragraph records how the drift was reviewed, not code that still runs). The shadow slice computed each query's class and the per-engine scores and first-assignment engine the class model gives, through the same resolver (`AssignmentResolver.resolve(..., pattern_model=...)`, never passed by a production caller), and wrote them per job as `assignment/v<N>/access_pattern_shadow.json` next to the assignment it shadowed; routing read none of it, and the routing snapshot did not change. The shadow also ran an attribution control that keeps every query's tables' own pattern scores through the same path, and moves found there come from scoring a pattern-only engine on the query's own tables, not from a class; the shadow and the switch PR list them apart from the class-driven moves (Decision 10). Until the switch, step 1's per-query check (`query_shape.single_table_access_shape`) kept its answers. The switch PR lists every moved query (sample, id, class, engine before and after, why) for wordpress, discourse and trailgear, with counts per class, for both the first and the final assignment (Decision 10), and is reviewed against the class table above, never tuned to a target distribution.

**Amendment 7 (2026-10-16, #728, #920, #985, the switch Amendment 5 planned): routing reads each query's own class score.** Every per-query score in the pipeline (the first assignment, the reality check, the cache owner, a model's flag, the customer gate and the post-schema reroute) takes its pattern dimension from the query's own access-pattern class, through one model, `src/agents/referee/query_pattern.py`'s `QueryPatternModel`, which `ScoringContext.from_pipeline` builds from the collector's schema keys and each engine's analysis weights; the shared scorer (`query_scoring.compute_query_confidence`) has no path without it. For a classified query the scorer reads no table's `pattern_match_score` or `confidence_score`: the table-inherited pattern score, each engine analysis's per-table pattern bonuses and the all-tables fallback leave routing for every engine alike, and stay only in the per-table summaries the deliverables show. A statement with no class (`utility`, `unparsed`) has no class score and keeps the pre-switch rule, as Amendment 5 says; on the bundled samples that is the utility statements, which the utility pin places anyway, and no bundled-sample statement: the 4 wordpress statements the SQL facade could not read when this switch landed (three truncated report digests and a `REPLACE INTO`) are classified since #986. The facade reads MySQL `REPLACE INTO` as the `INSERT` it is, and a digest the collector cut short up to its last complete predicate; because the cut-off predicates are not evidence of a key anchor, such a digest is never classed as key-anchored (`access_pattern._cut_short_class`: an aggregation, an unanchored join or an ad hoc filter, by its shape), and the key-access and attribute analyses do not read its pinned columns. The shadow artifact and its comparison runs are retired; the assignment writes `assignment/v<N>/access_patterns.json` instead, each query's class, reason, facts, class scores and parity-anchor notes (#936) as routing scored them, which routing reads none of. Criterion 4b holds for the pattern score (maintainer decision, 2026-10-16): no query's pattern score depends on another query on the same table; complexity and performance stay per table, and cost is per query since #494 (Decision 5).

Step 1 follows the class. `query_shape.single_table_access_shape` takes the query's class (`access_class`) and gives a read Amendment 5's answers: a key-scoped read that the text check alone finds relational because it is a key-anchored join, an aggregate with no `GROUP BY` over keyed rows, or a `GROUP BY` or `DISTINCT` that only de-duplicates is an ordered 1:M read (neutral); so are a range or an order over a key with no pinned value and a read with no predicate, which is no longer CRUD; a key lookup that only de-duplicates its rows is CRUD. Every other relational reason (a subquery, a CTE, an engine-specific function, a pattern match, a window function) keeps the read relational whatever its class, and a write keeps the text check. `aurora-anti-05`'s join participation no longer counts a key-anchored join.

Three class-table changes come with the switch (#920). A small reference-table read, every row of a table of at most 10,000 collected rows (`access_pattern.SMALL_TABLE_MAX_ROWS`, the limit DynamoDB's `metadata-config-store` reads too) with no predicate and no row limit, is its own class, rated by `metadata-config-store` (DynamoDB 90) and the range class's `pagination` (Aurora and DocumentDB 85); this is a proposed default, open to revision. `batch-in-list` (Aurora 70, with its sources) is listed for the key-lookup class and raises no score, since `key-value-lookup` rates the same read at 80. DynamoDB's `range-query` (90) counts in the key-scoped class only for a query that pins a key column of one table and ranges another of its columns (the classifier's `partition_range` fact, #933's shape, which the maintainer chose there); a join's range is not one. That fact has one definition, in the classifier, read by the class score, `key_access` and triage's range signal, and the range predicate has one definition too: `QueryFacts.range_predicate` is the access facts' ranges, with `regex_facts.RANGE_PREDICATE_RE` as its fallback, read by OpenSearch's time-range pattern; the two text definitions it replaces (`range_with_order_by`, `time_range_operator`) are deleted.

Six SQL features a query of any class can show have a home in the class scores too (#985, #984, #1102): recursive CTEs, `LATERAL` joins, stored routines, Aurora full-text search, upserts and JSON reads are listed under `[[features]]` in `src/catalog/access_classes.toml`, and each one's pattern (`cte-recursive`, `lateral-join`, `stored-routine`, `full-text-native` and `fulltext-search`, `upsert-conflict` and `upsert-duplicate-key`, `json-document-query`) rates a query, alongside its class's own patterns, only when the query shows the feature's fact (`recursive_cte`, `lateral_join`, `stored_routine`, `full_text`, `upsert`, `json_access`, read from the shared query facts in the source's dialect; a `lateral` word in a comment or a literal is not one). So the per-query score keeps the Aurora MySQL and Aurora PostgreSQL credits the catalog states for them (recursive CTEs 90 and 95, `LATERAL` 80 and 85, stored routines 70 each), and the JSON fits (Aurora PostgreSQL and Aurora MySQL 85, DocumentDB 80), wherever the class itself rates the engine lower; a JSON read is no longer a table-level complexity credit on any of the three engines (#1102), so a table where one query reads a JSON path no longer lifts its other queries (checked by `tests/unit/shared/test_routing_catalog.py`); no engine without a rating gains anything, and the numbers stay in the pattern files. A statement whose only content is a routine call (`EXEC`, `CALL`) reads no table, so it is a `utility` statement and keeps the pre-switch rule.

## What this ADR supersedes

- **ADR-017** — the per-query scoring unit (section 1) and configurable weights per target (section 4) stand; its model of specialist-curated, per-engine pattern catalogs with independent detection code is superseded by Decision 8's single, engine-neutral catalog and detector.
- **ADR-018** — the reality check as a consolidation step, and the human approval gate it feeds, stand; its description of the reality check computing engine fit through its own capability table and scoring logic is superseded by Decision 7.
- **ADR-021** — the general principle that a committed engine can absorb orphan queries from an engine that does not justify its cost stands as part of the reality check's consolidation role; its Aurora-specific absorption pass, with its own fitness gate and thresholds separate from the shared score, is superseded by Decision 7's single scoring path.
- **ADR-026** — folding the reality check into the assessment core, and the assignment-version resolution it introduced, stand unchanged; any description of the reality check's internal scoring logic as distinct from the resolver's is superseded by Decision 7.

## Consequences

### Positive

- One document that contributors and reviewers can read and check a routing change against, replacing scattered issue-comment decisions.
- A single scoring path for the first assignment and the reality check removes a class of bugs where the two disagreed for reasons that were not genuine consolidation.
- The pattern-first catalog makes every routing rule, for every engine, visible and comparable in one place, and makes adding an engine a configuration change rather than a code change to shared logic.
- DynamoDB's transaction support, and heterogeneous-source engine choice, are now stated decisions rather than implicit code behavior.

### Negative

- Building the catalog, unifying the two scoring paths, and making cost engine- and query-aware are each nontrivial changes to code that is already heavily depended on; they are sequenced as separate, independently reviewed and verified changes, not a single rewrite.
- How a co-dependency group's engine is chosen is explicitly left open by this ADR, so group routing can still disagree with what Decision 2 would pick for each member alone until that follow-up decision is made.

### Risks

- Migrating existing per-engine rules into the catalog risks silently changing a score if a rule is transcribed incorrectly; the per-query before/after reporting in Decision 10 is the mitigation.
- Neptune and Keyspaces placeholders could be mistaken for real support if a future contributor skips the "future enhancement" marking; the completeness check and the explicit `status` marking exist to prevent that.

## Alternatives Considered

- **Leave the model in issue comments.** Rejected: hard to find, easy to drift from, and no single place to check a routing PR against.
- **Rewrite the superseded ADRs in place.** Rejected: ADRs are a record of decisions as they were made. A new ADR that states what it supersedes keeps that history intact instead of erasing it.
- **Keep two independent scoring paths (resolver and reality check).** Rejected: the two paths drifted and disagreed on a large share of queries for reasons that were not intentional review logic, which is a correctness risk, not a feature.
- **Model Neptune and Keyspaces now instead of as placeholders.** Rejected for this round: in-flight data-movement work takes priority, and a placeholder still proves the catalog can hold a new engine.
