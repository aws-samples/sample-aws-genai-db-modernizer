# ADR-031: Query-First Routing Model and Engine Rule Catalog

**Status:** Accepted **Date:** 2026-10-11 **Deciders:** Database Modernizer Assessment Architecture Team **Related ADRs:** ADR-017 (Analysis Agent Scoring Framework), ADR-018 (Reality Check and Human Approval Gate), ADR-021 (Aurora Absorption Pass in Reality Check), ADR-026 (Fold Reality Check into the Assessment Core)

---

## Context

The routing model has been described across many issue threads rather than one document: how a query gets its engine, how the reality check consolidates engines, how co-dependency groups move, how cost factors into scoring, and how pattern-and-engine rules should be organized. Contributors and reviewers have had no single place to read the intended model or check a routing change against it.

An audit of the routing code against that intended model found that the model itself needed decisions, not just a write-up: whether cost is really a dimension of the score, how DynamoDB's transaction support should be scored, and how pattern and engine rules should be organized so one fact is not encoded in several places that can disagree. This ADR records those decisions. It does not record the audit's measurements, which belong to the tracking issues the audit filed.

Earlier ADRs described parts of this model before these decisions were made. ADR-017 introduced per-query scoring and per-target weights but predates engine-neutral detection and a declared cost dimension. ADR-018 introduced the reality check as engine consolidation, with its own capability and scoring logic separate from the resolver's. ADR-021 added an Aurora-specific absorption pass with its own fitness gate, inside the reality check. ADR-026 folded the reality check into the assessment core without changing how it scores a query. None of them described the query as the sole unit of assignment, a single engine- and query-aware cost dimension, or a pattern-first, engine-neutral rule catalog.

## Decisions

### 1. The query is the unit of assignment

Every routing decision is made per query. A table is an input to a query's score; it never decides a query's engine on its own. The engine recommended for a table in a table-level mapping is a summary, not ownership. No step may assign a query because of what other queries on the same table do: no table majority, no table owner, no table-wide classification. Counts, summaries and groups shown in deliverables are built from queries; a query group reported for a relational engine is a real group of queries, not a stand-in for a table.

### 2. A query's engine is decided in a fixed order

For each query and each candidate engine, the same five steps run in order:

1. **Candidates.** Every modeled target engine, minus any engine the source makes impossible. A homogeneous source always has its matching relational engine as a candidate. A heterogeneous source has exactly one relational engine as a candidate, chosen deterministically with the choice traced (see Decision 6).
2. **Capability gate.** An engine is excluded only if it is structurally unable to run the query at all. Poor fit is a score difference, not an exclusion, and every candidate is held to the same gate.
3. **Ownership gate.** An engine that is not a system of record cannot own a write or a locking read. A locking read is one that `query_shape.locking_clause` finds (#838), the same detector the shape check records (Decision 14): `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`, MySQL `LOCK IN SHARE MODE` or a SQL Server `UPDLOCK` / `HOLDLOCK` / `XLOCK` / `SERIALIZABLE` hint, never a lock word in a comment, a string literal or a quoted identifier. The UI engine picker runs a JavaScript copy held to the same cases.
4. **Score.** A weighted average of four dimensions — pattern match, complexity, performance and cost — computed from the query's own tables and its own matched pattern signals. A table-level classification may inform a query only through that query's own matched patterns, never by inheritance from the table.
5. **Penalties.** A penalty applies only to an engine that actually lacks the capability a pattern needs (see Decision 3). An engine that runs a pattern natively is not penalized for it.

The highest total score wins. On an exact tie, the source-compatible relational engine wins; no other engine preference exists. In the reality check, where a query already has a current engine (the first assignment has none), a tie that includes that current engine stays there instead: a tie is not a strictly higher score for some other engine, so moving the query would add a migration cost for no score benefit at all. This stability rule only ever applies when exactly one tied engine is the query's current one -- two different, still-tied current engines (members of the same co-dependency group sitting on two different engines) is not "the" current engine either way, and is reported as unresolved, not decided by which one sorts first. When neither the source-compatible rule nor stability resolves a tie, Decision 12 governs the placeholder pending the customer's own choice. Decision 13 applies the source-compatible rule to the reality check's choice of which engine to remove, including when the source-compatible engine scores higher by less than the unique-value margin.

Two second-level decisions apply after the per-query result: co-dependency grouping (Decision 4) and a small set of listed overrides for database administration statements and justified search pinning, which skip steps 3 to 5 under a stated condition only.

### 3. DynamoDB supports ACID transactions; the score reflects shape, not a missing capability

DynamoDB supports ACID transactions: `TransactWriteItems` and `TransactGetItems` give atomic, consistent behavior across up to 100 items, and a conditional write is itself ACID on a single item. A transaction is therefore not treated as a capability DynamoDB lacks. The score instead reflects how far the transaction's shape is from that native support: a transaction touching one or a few entities scores well, a wide multi-table transaction on a normalized model scores poorly because it needs a redesign. The decision trace states which shape a query matched and why.

This supersedes any treatment that scores DynamoDB transactions as a missing capability requiring a saga or workaround, in favor of the shape-based score above.

### 4. Co-dependency groups move as one unit

Queries that must move together — statements in one transaction, or reads that must stay consistent with a write — are placed as one unit once the group's engine is decided. Every member goes to that engine, even if a member alone would score higher elsewhere; each member's own best engine is still recorded in the trace. How the group's engine is chosen — for example, from the members' combined scores — is not decided by this ADR and remains open, to be settled with options when the grouping code next changes.

### 5. Cost is one of four weighted score dimensions, and is being made engine- and query-aware

Cost was already one of the four weighted dimensions of a query's score (pattern match, complexity, performance, cost), at a 40/30/20/10 default split, with some engines weighting cost differently. That weighting is unchanged by this ADR. What changes is how the cost dimension's value is computed: it is to be engine- and query-aware, factoring in the engine's standing cost shared across the queries it would serve, so that a low-traffic engine with high standing cost scores low on cost for a query it barely serves. The pricing shown in deliverable reports is a separate, unchanged presentation and is not derived from this scoring dimension.

### 6. Heterogeneous sources pick exactly one Aurora engine, deterministically

For a heterogeneous source (SQL Server, Oracle, DB2), exactly one of Aurora PostgreSQL or Aurora MySQL is the relational candidate for every query from that source. The choice is made deterministically, with the reasons traced, and feature support for a given query is checked against that chosen engine rather than assumed.

**Amendment 1 (2026-10-14, maintainer decision, #656): Aurora PostgreSQL wins only as the final exact-tie break.** The maintainer decision covers two points and only these: (a) for a heterogeneous source, neither Aurora engine is source-compatible by default (next paragraph); (b) Aurora PostgreSQL wins only when every existing check still leaves an exact tie on total adjusted score, traced as "tie between Aurora MySQL and Aurora PostgreSQL; PostgreSQL preferred on a tie by maintainer rule, ADR-031 Decision 6" (`aurora_choice.EXACT_TIE_RULE_REASON`). That is expected to be rare.

The existing checks that run before (b) predate this decision, and the decision does not change them. First, each engine's per-query scores are summed into a total. Per-operation support is already counted there, because the scorer's hard capability gate scores an engine 0 on a query it cannot serve. Next, the higher total wins outright when the totals differ by more than 5% of the larger one (`aurora_choice.MARGIN_RATIO`). Within that margin, or on an exact tie, a reported workload feature decides: sequences, recursive CTEs, MERGE, JSON or multiple schemas. With no workload feature, Babelfish compatibility decides for a SQL Server source. With neither, the higher total wins. Every one of these features currently favours Aurora PostgreSQL. Because every SQL Server source reports Babelfish, these checks send every SQL Server close call to Aurora PostgreSQL on dialect alone. The maintainer confirmed on 2026-10-14 that this is intended: Babelfish compatibility stays the tie-breaker within the margin for a SQL Server source (recorded on #445). The one-sided workload-feature step is still under review in #445 and is not part of this maintainer decision. As implemented today, (b) can only fire for an Oracle or DB2 source.

The chosen engine is not source-compatible. For a heterogeneous source, neither Aurora engine counts as source-compatible in Decision 2's tie rule or Decision 13's survival rule, whichever one this decision picks. Whether it can serve a given query depends on that query's own operations, not on the choice.

### 7. The reality check is the CTO consolidation review, routed by the same per-query scores

The first assignment can spread a workload across several engines because each fits some queries best. The reality check is the second-level review that asks, per engine already assigned: is this engine worth running for the queries it would serve, given its standing cost, its operational weight, and whether another engine already in the architecture serves those queries well enough? It may remove an engine or move its queries onto an engine already in the architecture. A moved query goes to its highest-scoring engine among the engines that remain, using the same per-query scores the first assignment used — the reality check does not keep a second, independent fit model. It reports every removed engine and every moved query with before and after scores, and claims a saving only for an engine the first assignment actually justified.

This supersedes the reality check's own independent capability and scoring logic (ADR-018) and the Aurora-specific absorption pass with its own fitness gate (ADR-021), replacing both with one scoring path shared with the first assignment. The reality check's role as engine consolidation and the human approval gate it feeds (ADR-018, ADR-026) are unchanged by this ADR.

When the mandatory-engine justification floor moves a query off an engine that failed it, a candidate already mandatory for a different engine (data already flowing to it via a signal override, such as a text-search sync) ranks ahead of an equally-scored, non-mandatory candidate (`reality_check_floors._find_best_absorber_for_query`'s `is_mandatory_secondary` bonus) -- a real operational reason (the data is already synced there) rather than a preference of convenience. It applies only after the score itself ties; an exact tie that survives it too still goes through Decision 2's tie-break, never decided by this bonus a second way.

### 8. Rules are a pattern-first, engine-neutral catalog in one place

Routing rules move out of per-engine code and into a declarative catalog read by every step: analysis, gates, penalties, scoring, cost, reality-check floors, reports and the UI.

- **One file per access-pattern type** (for example key-value lookup, full text search, transactions), each naming the pattern, the detector that identifies it, and one entry per engine with whether the engine supports the pattern, its score, and a short reason that feeds the decision trace. Each entry also has a `kind` (the engine's analysis reports the pattern as a fit or an anti-pattern; or, for an engine that does not report it, the engine has the needed capability natively, has a bounded redesign, takes the cross-engine penalty, or is unaffected), because support, score and reason alone cannot say which penalty or exemption applies. For a pattern backed by the hard capability gate, `supported` matches the gate engine by engine.
- **One file per engine** for properties that do not depend on the pattern: cost and pricing inputs, score dimension weights, justification floors, whether the engine can own writes, and its display name and color. Each engine file has a `status`: `active` (a routing target), `future` (a placeholder, Decision 9) or `legacy` (an id only older reports carry, such as the generic `aurora`; kept so those reports still render, never a routing target).
- **Detection stays in code and is engine-neutral.** A detector runs once per query and reports facts (for example a transaction's entity count, or a wildcard's position), not scores. The catalog turns those facts into each engine's support and score, so a given fact is classified the same way regardless of which engine is being scored, and engines differ only in their catalog entries. This removes the previous pattern, where each engine's analysis detected and scored its own patterns independently, which let the same fact be encoded in more than one place with disagreeing answers.
- **Validation.** The catalog loads into typed models at start-up, so a missing or mistyped field fails loudly. A completeness check requires every pattern file to have an entry for every engine, so adding an engine or a pattern fails with the exact list of missing decisions instead of silently defaulting to "unsupported."
- **Comparison.** A rendered pattern-by-engine matrix, with support, score and reason, plus the engine properties side by side, is the one place that answers "why does this engine's score differ from that one's for this pattern?" Display names and colors used elsewhere are generated from the engine files rather than kept as separate copies.
- **Adding an engine** means one engine file, one entry per pattern file (the completeness check lists exactly which), and the engine's own detection code where a pattern has no existing detector. No change to the resolver, the reality check, the reports or the UI.

### 9. Neptune and Keyspaces are future placeholders

Neptune and Keyspaces are added to the catalog as placeholders only, each marked as a future enhancement with an explicit "not modeled yet" entry in every pattern file so the completeness check passes on a recorded decision rather than a default. A placeholder engine is never a routing candidate and routing output is unchanged by its presence. Modeling either engine for real — giving it real scores, detection and schema-design support — is separate, later work.

### 10. Every routing change reports its per-query effect

A routing change reports, before and after against the prior behavior, the per-query effect on every available sample workload, for both the first assignment and the final (post-reality-check) assignment. Engine totals alone are not sufficient evidence. If a score-based result looks wrong, it is reported as a finding, not silently corrected with a bias toward a preferred engine.

**Amendment 3 (2026-10-14, planned design decision from the #489 routing plan, #616): every engine change is a ledger entry.** A query's engine (`assigned_engine`) and its unresolved tie (`tied_engines`) change in one place only: `move_ledger.apply` / `apply_to_assignment` (`src/agents/referee/move_ledger.py`), which records a Move (`src/contracts/move_ledger.py`) naming the pass, the rule, the engine the query left and the one it lands on, the shared scorer's scores on both, the runner-up, the evidence the pass saw and who caused it (a rule, the customer or a model's flag). The ledger also holds each query's current tie (`MoveLedger.tied`), and the first assignment builds v1's ties from it. Each assignment version carries exactly the Moves that produced it (`Assignment.moves`, per version), and replaying the version it was derived from (nothing, for v1) plus those Moves rebuilds its engines and ties; every writer of a version (the first assignment, the reality check, the customer gate, the post-schema router's reroute and rollback) checks that with `move_ledger.check_replay` before writing and refuses a version that does not replay. The cache owner normalisation of an assignment written before the cache overlay is a Move too (`cache_owner_normalize`), wherever it runs. This is how this decision's per-query report reads one record instead of several that can disagree. No module other than `move_ledger.py` may write `assigned_engine` or `tied_engines`, and the guard has no exceptions. The post-schema router's reroute version records one `post_schema_flag` Move per moved query (rule `flag.capability_gap`, actor `model_flag`, #489 Track L PR4); when the redesign on it fails, the rollback version that restates the earlier routing records the reverse Moves, one per Move of the reroute, undone in reverse order back to the engine and tie the query had (rule `rollback.redesign_failed`, actor `rule`, #770); its replay check compares the result with the restated version, so a query that differs without having been rerouted is refused. One replay rule covers every version. The reality check's own records are derived from its Moves rather than kept beside them (#616): each consolidation record is a net move the Moves replay to, a sanity-sweep `removed` verdict and its records come from the sweep's Moves, and a `moved` flag verdict takes its destination and scores from its Moves. What a Move does not carry stays computed where it is decided: the pass's reason text, the retained queries of a partial consolidation (a query that did not move has no Move), the removed engine's analysed cost (the saving, counted once per engine) and its first-assignment `workload_justified` verdict, and the `kept` sweep and `kept`/`ignored` flag verdicts, which move nothing. This records the design decision of the #489 routing plan (Track L); it is not a separate maintainer decision.

### 11. Models explain; they do not decide

Assignment and reality-check routing remain deterministic. A model may explain an assignment in natural language; it never decides or changes one. Running without a model gives the same assignment and reality-check result as running with one.

**Amendment 2 (maintainer decision, 2026-10-14, #647, #629): a model's flag is evidence; the scorer decides.** A model may flag queries it judges an engine unable to serve, in one structured shape for both LLM modes (`src/contracts/model_flag.py`: the query ids, the engine they are on, a reason category and a short explanation). A flag never names a destination. An accepted flag marks the flagged engine unable to serve those queries, a capability gap for those queries only (`ScoringContext.flag_gaps`), and the shared scorer re-routes them to the best engine that may own them, with exact ties through `tie_break.break_tie` and co-dependency groups moved as one unit (`src/agents/referee/model_flags.py`). The before and after scores are recorded with the flag. A reality-check flag re-routes its queries only among the engines the reality check kept: it never brings back an engine the check removed and never re-settles any other query. When no kept engine can take them, the queries stay where they are and the record says why. The same holds after schema design (#629): the reality check consolidates first, and schema design and PE review work on the assigned queries. A PE reviewer's routing flag (or a designer's unsupported pattern) counts only for a query on the reviewer's own engine, and the post-schema router re-routes it, with its co-dependency group, only among the engines the approved assignment keeps. A reroute writes a new assignment version (`source = post_schema_routing`, status `rerouted_after_approval`, never the customer's approval it edits), and schema design runs again on that version for every engine the moves touch (the one a query left and the one it joined), so the design and the assignment agree. Every deliverable lists the queries moved after approval, why, and how to override them; the run does not pause for a new approval. A model therefore still never decides an assignment: a run with flags differs from a run without a model only where a flag removed an engine from a query's candidates, and a run with no flags gives the same result as a run with no model.

### 12. A still-unresolved tie gets a placeholder, decided by settled workload share then a stable hash (maintainer decision, 2026-10-12)

Decision 2 leaves some ties with no rule at all: no tied engine is source-compatible, and (in the reality check) no tied engine is the query's current one either, or two different tied engines are each current for different members of the same co-dependency group. The query still needs an engine to sit under until the customer picks one, so a placeholder is used -- but the placeholder is not itself a new ADR-031 preference, and the structured, customer-visible fact is the tie itself (`QueryAssignment.tied_engines`), never silently hidden behind the placeholder's pick.

The placeholder, in order: first, whichever tied engine already carries more of the SETTLED workload for this run -- the number of queries this run decided without a tie (never another placeholder pick, so one tie's placeholder can never feed another tie's count, which would make the result depend on evaluation order); second, when that count is also tied (including the common case where neither engine has any settled workload yet), a stable hash of the query id and the candidate engine name. Favoring the engine with more settled workload is consolidation-consistent with Decision 7's CTO review, which already prefers fewer, larger engines over more, smaller ones -- it is not a preference for one engine's name or brand. The hash fallback exists only so the result is deterministic across runs on the same input; it is a hash OF the engine's name together with the query id, not a comparison BY the name -- an engine's name, traffic or query count is never read to decide which one wins by being who it is, only hashed alongside the query id to pick a stable, unpredictable split when the settled-workload count cannot.

A tied query is evidence for exactly the ONE engine the placeholder picks -- never for every tied engine, and never for none. Phase 1 counts it as that one engine's native workload when deciding whether the engine earns its place; excluding it from every engine's evidence could leave an engine whose only queries were tied uncommitted with no fallback (crashing the placement invariant when nothing else was eligible either) or let a tied workload silently fall to a far weaker committed engine because Phase 1 never got to evaluate either tied engine at all. The query still carries `tied_engines` and stays visible to the customer either way. If the picked engine is later removed anyway, Phase 2 re-resolves the tie among whichever of the originally tied engines are still committed, never opening the choice to the wider committed set while at least one of them survives; only once none of the tied engines survive does the query fall back to its best-scoring surviving engine among the rest, with an honest reason, and `tied_engines` clears -- the tie is genuinely gone, not re-placeholdered.

Eligibility gates that key off "the query's current engine" (the specialist-absorb exemption, the join-consolidation block) treat every one of a tied query's `tied_engines` as current, not just the one placeholder happens to be recorded as -- otherwise an arbitrary placeholder pick could silently decide a gate's answer instead of just sitting the query somewhere pending the customer's choice. The same stable key (sorted member ids for a co-dependency group, never input order) feeds the placeholder's hash fallback everywhere it is used -- the first assignment, the reality check's placement step, and its mandatory-engine-floor absorber -- so the same tie cannot re-pick a different engine purely because of evaluation order.

This is implemented once, in `tie_break.pick_unresolved_tie_placeholder`, so the resolver, the reality check's placement step, its mandatory-engine-floor absorber and its eligibility gates cannot drift from each other on it; the settled-workload snapshot itself is computed once, by the resolver, and persisted for the reality check to reuse (`RoutingTrace.settled_counts`) rather than each stage measuring "settled" differently. A future ADR-031 amendment may replace this placeholder; until then, this is the one rule governing it.

### 13. The source-compatible engine is not removed on cost for an engine that serves its queries no better, unless that engine is much cheaper (maintainer decision, 2026-10-13)

Decision 2's tie rule also governs which engine the reality check removes, not only where a query goes, and it extends to a margin too small to count as unique value: nobody chooses a NoSQL engine over the source-compatible SQL engine for a small saving. When the source-compatible Aurora engine scores every one of its queries equal to or higher than its best other committed engine, the reality check keeps it instead of removing it on standing cost. Before this decision, Phase 1 removed the engine with the highest burden per unique query, so Aurora's $250 standing cost against DocumentDB's $200 removed Aurora from a workload it served at least as well, on a $50 difference (#600).

The one exception: the alternative is at least 40% cheaper in standing cost AND saves at least $100 a month. Both conditions must hold, and each is inclusive at its boundary. Aurora at $250 against DocumentDB at $200 is 20% and $50, so Aurora stays; against DynamoDB at $0 it is 100% and $250, so the cheaper engine wins. The alternative for a query is its best-scoring other committed engine (every one of them, when several score the same); the exception must hold for every one of the source-compatible engine's queries through at least one of its best alternatives.

The rule applies only when the source-compatible engine scores at least as well on every one of its queries. If any query scores lower on it than on another committed engine, the existing rules (unique value, then the burden rank) decide as before. This is the only place standing cost is weighed against the source-compatible engine's score; it is implemented once, next to the shared tie-break, in `tie_break.source_compatible_engine_survives`, with both thresholds as named constants (`tie_break.CHEAPER_ENGINE_MIN_SAVING_SHARE`, `tie_break.CHEAPER_ENGINE_MIN_SAVING_MONTHLY`).

A heterogeneous source (SQL Server, Oracle, DB2) has no source-compatible engine, so this rule does not apply to it; the one relational engine Decision 6 chooses for it gets no protection from standing cost under this decision. This was confirmed on 2026-10-14 (#656, see the Decision 6 amendment).

### 14. A whole-workload anti-pattern's table-level rule only complements the per-query check (maintainer decision, 2026-10-14, #692)

Some catalog anti-patterns are defined over a table's whole workload. Today those are `aurora-anti-05` ("no-relational-need": no foreign keys, no join participation, every application query single-table CRUD) and `aurora-anti-06` ("single-access-pattern-table": at most 2 application queries, all single-table, all by primary key or a single column filter, no foreign keys; #714). For `aurora-anti-06`, "by primary key or a single column filter" means the shared per-query CRUD check below (`query_shape.single_table_access_shape`), not a separate count of filter columns. Such an anti-pattern runs in two steps, always in this order:

1. **The per-query check, first.** Each application query on the table is classified on its own access pattern (`query_shape.single_table_access_shape`):
   - **CRUD**: a point or simple-key read or write. `ORDER BY <the table's own primary key>` with a literal single-row limit is a key-value lookup and counts, in every spelling: `LIMIT 1`, `TOP 1` / `TOP (1)`, `FETCH FIRST|NEXT [1] ROW(S) ONLY` (no count means 1), MySQL `LIMIT 0, 1`, and an explicit `OFFSET 0` (`LIMIT 1 OFFSET 0`, the T-SQL `OFFSET 0 ROWS FETCH NEXT 1 ROWS ONLY`). The same holds at any offset, literal or placeholder: `LIMIT 1 OFFSET 5`, `LIMIT 1 OFFSET $1`, `OFFSET m LIMIT 1`, MySQL `LIMIT 5, 1` / `LIMIT ?, 1`, and `OFFSET n ROWS FETCH NEXT 1 ROW ONLY` with `n` a literal or a placeholder.
   - **Ordered 1:M read**: the same primary-key-ordered read with any other limit: `LIMIT n` with n > 1, a bind-parameter limit with no evidence it is 1, `TOP n PERCENT` (`TOP (1) PERCENT` included), or `WITH TIES` (which can return more than n rows), with or without an offset (`LIMIT 5 OFFSET $1`, `OFFSET 5 ROWS FETCH NEXT 1 ROW WITH TIES`). A key-value store models it, so it is neutral: neither CRUD evidence nor relational evidence. It is never labelled a key-value lookup. A neutral read gives no relational need, so a per-table rule such as `aurora-anti-05` or `aurora-anti-06` may still apply to it (step 2). (These lists spell out the 2026-10-14 maintainer rule, "a literal single-row limit is key-value; a placeholder or any other number is neutral", for every row-limit form; #782. Clarification, maintainer decision of 2026-10-15 posted on #782 (#857): a single row from a known table at any offset is a key-value lookup, not a neutral read. It supersedes the 2026-10-14 reading that any skip, even with a limit of 1, makes the read neutral. A read that skips locked rows is still at most neutral, see below.)
   - **Relational**: anything else. A relational query never takes the penalty.
   - **A locking clause does not change the shape** (#799; Decision 3: DynamoDB supports transactions, so the score reflects shape). `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` (with `OF` or `NOWAIT`), MySQL `LOCK IN SHARE MODE` and a SQL Server `WITH (UPDLOCK | HOLDLOCK | XLOCK | SERIALIZABLE ...)` hint lock the rows a read returns. They do not change which rows those are, and `NOWAIT` changes only what happens when a row is already locked. A query is classified as the same read without the lock: a locking point read by key, or a locking `ORDER BY <primary key>` read with a literal single-row limit, is CRUD; a locking read in primary-key order with any other limit is an ordered 1:M read; a locking range, aggregate or non-key-ordered read stays relational. The exception is a lock that skips rows: `SKIP LOCKED` and the T-SQL `READPAST` hint return the first row no other transaction holds (a work-queue claim), not the row the key or key order names. That is an unknown row (an offset, by contrast, names a position in a known order, #857), so it is at most an ordered 1:M read and never CRUD, with or without an offset; relational evidence stays relational. The lock is recorded separately as a transactional need (`query_shape.locking_clause`, the `locking_clause` field of each query in the Aurora decision traces, with hint names limited to the fixed SQL Server table-hint list). It adds no penalty or bonus to any engine. Keeping a locking read off an engine that is not a system of record is a separate ownership rule (Decision 2 step 3, `cache_overlay.is_locking_read`); it reads the lock with this same `locking_clause` (#838). A lock word in a comment, a string literal or a quoted identifier (a column named `"update"`) is not a lock. (Engineering decision under Decision 3, open for maintainer review on #799.)
2. **The table-level rule, as a complement.** The anti-pattern's own table condition (for `aurora-anti-05`, no foreign keys and no join participation; for `aurora-anti-06`, at most 2 application queries and no foreign keys) can add the penalty only when step 1 found no relational query on the table. Ordered 1:M reads are neutral here too: they neither block the rule nor are needed for it, so a table whose application queries are all ordered 1:M reads is treated exactly as it would be without this classification. The penalty then covers the table's CRUD and ordered 1:M queries, because neither has a relational need. It never overrides a per-query result.

Why the table-level rule exists at all: the catalog rule is a negative claim about the table, that it needs nothing relational. One aggregate, window function, subquery, range or unkeyed write, or ordering over non-key columns on the table makes that claim false. Penalising the table's keyed reads and writes while its relational queries stay on the relational engine would split one table's writes across two engines (the `web_crawler_requests` case found in #686's review). The table-level rule never assigns a query and never adds to a score. It only gates that one penalty, and every query is still scored from its own tables (Decision 1). The per-query facts underneath are engine-neutral and defined once (Decision 8).

A new anti-pattern may use a table-level rule only if its catalog text defines it over the table's whole workload, and only in this order: per query first, then table.

## Enforcement

Each decision names the guard test that fails when the code stops following it. `tests/unit/docs/test_adr_enforcement.py` fails when a decision has no row here, or when a row names a test file, class or function that does not exist. A decision with no guard yet says `none yet` and the issue that will add one; it is never left blank.

## What this ADR supersedes

- **ADR-017** — the per-query scoring unit (section 1) and configurable weights per target (section 4) stand; its model of specialist-curated, per-engine pattern catalogs with independent detection code is superseded by Decision 8's single, engine-neutral catalog and detector.
- **ADR-018** — the reality check as a consolidation step, and the human approval gate it feeds, stand; its description of the reality check computing engine fit through its own capability table and scoring logic is superseded by Decision 7.
- **ADR-021** — the general principle that a committed engine can absorb orphan queries from an engine that does not justify its cost stands as part of the reality check's consolidation role; its Aurora-specific absorption pass, with its own fitness gate and thresholds separate from the shared score, is superseded by Decision 7's single scoring path.
- **ADR-026** — folding the reality check into the assessment core, and the assignment-version resolution it introduced, stand unchanged; any description of the reality check's internal scoring logic as distinct from the resolver's is superseded by Decision 7.

## Consequences

### Positive

- One document that contributors and reviewers can read and check a routing change against, replacing scattered issue-comment decisions.
- A single scoring path for the first assignment and the reality check removes a class of bugs where the two disagreed for reasons that were not genuine consolidation.
- The pattern-first catalog makes every routing rule, for every engine, visible and comparable in one place, and makes adding an engine a configuration change rather than a code change to shared logic.
- DynamoDB's transaction support, and heterogeneous-source engine choice, are now stated decisions rather than implicit code behavior.

### Negative

- Building the catalog, unifying the two scoring paths, and making cost engine- and query-aware are each nontrivial changes to code that is already heavily depended on; they are sequenced as separate, independently reviewed and verified changes, not a single rewrite.
- How a co-dependency group's engine is chosen is explicitly left open by this ADR, so group routing can still disagree with what Decision 2 would pick for each member alone until that follow-up decision is made.

### Risks

- Migrating existing per-engine rules into the catalog risks silently changing a score if a rule is transcribed incorrectly; the per-query before/after reporting in Decision 10 is the mitigation.
- Neptune and Keyspaces placeholders could be mistaken for real support if a future contributor skips the "future enhancement" marking; the completeness check and the explicit `status` marking exist to prevent that.

## Alternatives Considered

- **Leave the model in issue comments.** Rejected: hard to find, easy to drift from, and no single place to check a routing PR against.
- **Rewrite the superseded ADRs in place.** Rejected: ADRs are a record of decisions as they were made. A new ADR that states what it supersedes keeps that history intact instead of erasing it.
- **Keep two independent scoring paths (resolver and reality check).** Rejected: the two paths drifted and disagreed on a large share of queries for reasons that were not intentional review logic, which is a correctness risk, not a feature.
- **Model Neptune and Keyspaces now instead of as placeholders.** Rejected for this round: in-flight data-movement work takes priority, and a placeholder still proves the catalog can hold a new engine.
